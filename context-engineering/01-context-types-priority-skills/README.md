# 1장. 컨텍스트의 종류와 우선순위 — 역할 분리 · 출처 표지 · 제외 사유 먼저 · Skills

> 2026-10-28 학습 기록. Context Engineering 1일차 오전 수업입니다. 같은 질문("13만원짜리 숙소를 예약해도 정산할 수 있나요?")에 필요한 입력을 지시·질문·문서·도구 결과·메모리로 나누고(1-1), 후보 자료 중 무엇을 쓸지 범위 → 유효성 → 관련성 순서로 고르는 법과 필요한 절차만 불러오는 Skills를 실습했습니다(1-2).

## 학습 목표

- Prompt Engineering · RAG · Context Engineering이 각각 무엇을 묻는지 구분한다.
- 자료의 종류(`kind`, 앱이 정함)와 메시지 역할(`role`, API가 정함)을 구분하고, 지시는 system · 자료와 질문은 user에 넣는다.
- 자료를 묶을 때 `[id / kind / source]` 출처 표지를 붙인다.
- 관련성 점수보다 **접근 범위 · 유효성 · 일관성**을 먼저 확인하고, 통과한 것끼리만 점수로 정렬한다.
- 중복과 충돌을 다르게 처리하고, Skills는 질문에 맞는 절차만 고른다는 것을 안다.

## 전체 흐름

### 한 문장

**프롬프트 엔지니어링이 "content에 들어갈 글을 잘 쓰기"라면, 컨텍스트 엔지니어링은 "무엇을 얼마나 넣을지 고르기"입니다.** RAG 1~9장의 검색·중복 제거·예산·Parent 확장·압축이 사실상 컨텍스트 엔지니어링이었어요.

```text
질문 하나에 필요한 입력
 ├─ 서비스 지시 (system)        근거로 답하고 단정하지 않기
 ├─ 현재 질문   (user)          13만원 숙소 정산 가능?
 ├─ 검색 문서   kind=document   1박 12만원 · 영수증 · 초과 시 서면 승인
 ├─ 도구 결과   kind=tool_result 승인 내역 확인되지 않음
 ├─ 메모리      kind=memory     한국어로 간결한 설명 선호
 └─ 이전 대화                   어느 출장·예약인지

고르는 순서: 접근 범위 → 유효성(현행·만료) → 일관성 → 관련성(점수) → 예산(3장)
```

### 용어 정리 (질문하며 정리)

| 용어 | 뜻 | 예 (RAG 6장) |
| --- | --- | --- |
| instruction | 모델에게 어떻게 하라는 규칙 | "근거로만 답하고, 없으면 insufficient" |
| question | 사용자가 실제로 물은 것 | "출장 숙박 한도는?" |
| context | 답할 때 참고하라고 넣는 **자료** | `[S1] 제목\n본문` |
| messages | 재료를 역할별로 담는 그릇(리스트) | `[{"role": "system", …}, {"role": "user", …}]` |
| content | 메시지 하나의 **실제 내용 칸** | `{"role": "system", "content": instruction}` |

- messages(목록) → 메시지(role + content) → content 안에 instruction / question / context를 담아요.
- **context**(참고 자료라는 종류)와 **content**(메시지의 칸 이름)는 다른 말이에요. RAG 6장 `response.json()["message"]["content"]`도 모델이 쓴 content를 꺼낸 것.
- 둘은 항상 같이 써요. 지시가 좋아도 근거가 빠지면 틀리고(RAG 9-1 예산 70), 근거가 완벽해도 "없으면 보류" 지시가 없으면 지어내요.

## 핵심 이론

### 1. 입력 구성과 역할 분리 (1-1강)

| 관점 | 주로 묻는 질문 |
| --- | --- |
| Prompt Engineering | 어떻게 지시하고 어떤 형식으로 답하게 할까? |
| RAG | 어떤 문서를 찾아 근거로 쓸까? |
| Context Engineering | 이 요청에 필요한 **전체 입력**을 어떻게 관리할까? |

- `kind`(document · tool\_result · memory)는 앱이 정하고, `role`(system · user · assistant · tool)은 API가 정해요.
- 자료를 넣기 전에 두 가지를 물어요: ① 무엇을 알려 주나? ② **모델의 행동을 지시할 권한도 있나?** → 문서 속 명령문은 지시가 아니에요(4-2 Prompt Injection으로 이어짐).
- 출처 표지: `[policy-v2 / document / 출장 규정 v2]` + 본문. 자료 ID·버전·선택 이유·제외 이유는 기록하되 비밀 값이나 제외한 원문 전체는 로그에 남기지 않아요.
- 컨텍스트에 규정을 넣는 건 **모델 학습이 아니에요.** 다음 요청에서 쓰려면 다시 조회하거나 상태를 전달해야 해요.
- 메모리를 system에 넣는다고 더 잘 기억하는 게 아니에요. 위치보다 **출처와 권한**이 중요하고, 선호를 절대 규칙으로 올리면 오염된 기억이 행동을 바꿔요.

### 2. 우선순위와 입력 조립 (1-2강)

| 판단 | 확인할 내용 | 출장 질문의 예 |
| --- | --- | --- |
| 접근 범위 | 현재 사용자·조직이 읽을 수 있나 | 다른 사용자의 선호는 제외 |
| 유효성 | 현재 적용되는 자료인가 | 구버전·만료된 메모 제외 |
| 일관성 | 같은 사실을 다르게 말하지 않나 | 현행 규정 두 개의 한도가 다르면 확인 |
| 관련성 | 이 질문에 필요한가 | 숙박 한도와 초과 승인 조건 |
| 예산 | 전체가 한도에 들어가나 | 3장 |

```text
후보 5개 (기준일 2026-10-08)
travel-old     shared · retired   0.99  → 현행 문서 아님
travel-v2      shared · current   0.90  → 선택 ①
approval-rule  shared · current   0.85  → 선택 ②
other-memory   mina · current     1.00  → 사용자 범위 불일치
temporary-note jihoon · ~10-01    0.95  → 유효기간 만료
```

- **점수가 가장 높은 둘이 먼저 빠져요.** 관련성 점수는 범위·유효성·일관성을 통과한 자료끼리만 비교해요. 실제 서비스는 검색 쿼리·저장소 조회 단계에서 권한 필터를 걸어요.
- 중복 vs 충돌: ID·버전·본문이 같으면 한 번만 넣고 출처 연결 유지 / 같은 ID인데 본문이 다르면 갱신·식별자 문제 / 현행 규정끼리 한도가 다르면 범위·시행일을 비교하고 **단정 보류** / 한도 문서와 승인 문서는 서로 보완.
- 검색 점수는 규정의 옳고 그름을 판정하지 않아요. 버전 숫자가 크다고 최신으로 정하지도 않아요.

### 3. Skills (1-2강)

```python
chosen = [s for s in skills if any(w in question for w in s["keywords"])]
# "출장 숙박 한도를 알려 주세요." → ['travel']
```

- 필요한 절차만 골라 불러와요. 하나면 절차 + 현재 규정 + 승인 조회, **없으면 임의 절차를 적용하지 말고** 질문 재확인, 여럿이면 복합 질문인지 모호한지 확인.
- Skill을 골랐다고 그 안의 명령을 다 실행하지 않아요. 신뢰된 저장소의 절차인지, 사용자에게 권한이 있는지, 인자가 맞는지는 따로 확인.

### q1\_hard: 질문에 필요한 자료만 조립

```python
docs = [item for item in context if item["kind"] == "document"]      # ['policy-v2']
new_messages = [
    {"role": "system", "content": instruction},

]
```

- "영수증이 필요한가요?"에는 규정 문서만 필요해요. approval-17·preference-1을 빼면 입력이 짧고 혼선이 줄어요.

### q2\_hard: 기준일을 9/30으로 바꿔 다시 고르기

```python
picked = [doc for doc in documents if exclusion_reason(doc, current_user, as_of) is None]
picked.sort(key=lambda doc: (-doc["score"], doc["id"]))   # 동점이면 id
# temporary-note(0.95), travel-v2(0.90), approval-rule(0.85)
```

- `doc`은 lambda의 **매개변수 이름**(리스트 항목 하나). `def sort_key(doc): return (-doc["score"], doc["id"])`와 같고, 이름은 `x`로 바꿔도 동작해요.
- sort가 항목마다 key 튜플을 만들어 작은 순으로 줄 세워요. 첫 칸이 `-score`라 점수 **큰** 순, 같으면 둘째 칸 `id` 알파벳 순(동점 처리).
- 예: b(0.9), a(0.9), c(0.7) → 키 (−0.9,"b"), (−0.9,"a"), (−0.7,"c") → a, b, c. RAG 7장 bm25의 `key=lambda r: (-r["score"], r["chunk_id"])`와 같은 패턴.
- 기준일을 9/30으로 당기면 10/01 만료 메모가 아직 유효해서 들어와요. 하지만 "지난 예약의 임시 메모"가 숙박 한도 질문에 정말 필요한지는 관련성으로 다시 봐야 해요.

### CE1-Q5. 서술형 — 프롬프트 엔지니어링 vs 컨텍스트 엔지니어링

<details>
<summary>예시 답안</summary>

프롬프트 엔지니어링은 content에 들어갈 글을 잘 쓰는 일이에요. "근거로만 답하고 없으면 insufficient", JSON Schema·enum 출력 형식, `[S1]` 라벨 같은 user content의 모양이 여기에 해당해요. 컨텍스트 엔지니어링은 무엇을 얼마나 넣을지 고르는 일이에요. 검색, `chunk_id` 중복 제거, 문자 예산, Parent 확장·압축, 대화 기록·기억 선택, 캐시를 고려한 배치가 여기에 해당해요. 지시가 좋아도 예산 때문에 승인 조건이 빠지면(9-1 예산 70) 틀린 답이 나오고, 근거가 완벽해도 "없으면 보류" 지시가 없으면 모델이 지어내요. 그래서 둘은 항상 같이 써요.

</details>
