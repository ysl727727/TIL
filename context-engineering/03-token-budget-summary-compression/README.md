# 3장. 토큰 예산과 압축 — chat template로 세기 · Sliding Window · 구조화 상태 · 원문 추출

> 2026-10-28 학습 기록. Context Engineering 1일차 오후 수업입니다. 글자·바이트·토큰을 구분하고 실제 모델 토크나이저(Qwen3)와 chat template로 전체 입력을 세서, 출력 공간을 먼저 남긴 뒤 최근 턴부터 담는 Sliding Window를 만들었고(3-1), 대화를 현재 값·이전 값·출처로 정리하고 긴 문서를 원문 문장 ID와 함께 압축한 뒤 빠진 근거를 확인했습니다(3-2).

## 학습 목표

- 문자 수 · 바이트 수 · 토큰 수의 차이를 알고, 한도 검사는 **실제로 쓸 모델의 토크나이저**로 한다.
- `apply_chat_template(..., tokenize=True, add_generation_prompt=True)`로 역할 표시까지 포함한 전체 입력을 센다.
- 입력 예산 = 요청 한도 − 출력 예약 − 여유분을 계산하고, 질문·답변을 한 턴으로 묶어 최근 연속 구간을 남긴다.
- 구조화 상태(현재 값 · 이전 값 · 출처)와 원문 추출 압축을 구현하고, 압축 뒤 빠진 근거를 집합 차로 확인한다.
- 한 번에 넣기 어려운 문서를 Map → Reduce로 나눠 줄이는 절차를 안다.

## 실습 파일

| 강 | 주제 | 실습 상태 |
| --- | --- | --- |
| 3-1 | 토큰 예산과 Sliding Window — `count_tokens`, `select_recent`, 한도 256·512·1024 | ✅ `lesson_01.py` · q1\_hard 통과 |
| 3-2 | Conversation Summary와 긴 문서 압축 — 현재·이전 값, `missing_evidence`, Map/Reduce | ✅ `lesson_02.py` · q2\_hard 통과 |

3-1은 첫 실행 때 Qwen3 토크나이저 파일만 받아요(모델 가중치 없음). 수업 전에 `revision`을 고정해 미리 캐시해 뒀어요.

## 전체 흐름

```text
글자 5 · 토큰 3 ("안녕하세요")
 → count_tokens = len(apply_chat_template(messages))   역할·응답 시작 표시까지
 → 입력 예산 = 한도 − 출력 예약 − 여유분
 → select_recent: 최신 턴부터 넣어 보고 넘치는 순간 멈춤
      256 → 1턴 / 512 → 6턴 / 1024 → 6턴
 → 그래도 길면 줄이기
      구조화 상태: 담당자·마감일·예산 = 현재 값 + 이전 값 + 출처
      원문 추출:   [p1] … [p4] 문장 ID + 원문 → missing_evidence로 누락 확인
      너무 길면:   Map(부분 요약) → Reduce(묶어서 다시 요약)
```

## 핵심 이론

### 1. 무엇을 세나 (3-1강)

| 단위 | 무엇을 세나 | 쓰임 |
| --- | --- | --- |
| 문자 수 | 코드 포인트 수 | 글자 길이 안내 |
| 바이트 수 | UTF-8 등 인코딩 크기 | 파일·전송 크기 |
| 토큰 수 | 지정한 토크나이저가 만든 ID 수 | 모델의 입력·출력 예산 |

- 다른 모델의 토크나이저로 센 값을 현재 모델 사용량으로 해석하지 않아요. 같은 토큰 수를 재현하려고 토크나이저 `revision`도 고정해요.
- 본문 길이 합 ≠ 모델이 읽는 길이. chat template이 붙이는 역할 표시와 `add_generation_prompt`의 응답 시작 표시까지 들어간 **최종 목록**으로 검사해요(딥러닝 심화 8장 Chat Template과 연결).

### 2. 출력 공간 먼저, 턴 단위로 (3-1강)

```text
입력 예산 = 요청 한도 − 출력 예약량 − 여유분
512 − 128 − 32 = 352
```

- 도구 명세, 도구 호출·결과, 메모리·요약도 입력에 넣는 순간 예산을 써요.
- 질문과 답변을 한 턴으로 묶어 **최신 턴부터** 넣어 보고 넘치면 멈춰요. 도구 대화라면 호출 · 결과 · 후속 메시지까지 한 단위.
- "최근 메시지 10개만 남기면?" → 메시지 길이가 제각각이라 **개수로는 한도를 보장할 수 없어요.**
- 고정 지시와 현재 질문만으로 예산을 넘으면 바로 `ValueError`로 알려 줘요.

```text
요청 한도=256,  입력 예산=96,  사용=85,  남은 턴=1   → "예산은 1억 2천만원이에요." 하나뿐
요청 한도=512,  입력 예산=352, 사용=265, 남은 턴=6
요청 한도=1024, 입력 예산=864, 사용=265, 남은 턴=6
```

- 256일 때는 길이는 통과했지만 담당자·마감일 근거가 없어요. **길이 통과와 근거 보존은 다른 조건**이에요(RAG 9-1 예산 70과 같은 이야기).

### 3. 무엇을 남길까 (3-2강)

| 방식 | 잘 보존하는 것 | 주의할 점 |
| --- | --- | --- |
| 최근 대화 | 직전 흐름 | 오래된 결정·조건이 빠짐 |
| 문단 요약 | 큰 흐름 | 조건·최신 값이 흐려짐 |
| 구조화 상태 | 담당자·기한·금액 같은 항목 | 필드로 안 정한 맥락이 빠짐 |
| 원문 추출 | 숫자·예외·정확한 문구 | 문장 선택을 잘못하면 근거가 빠짐 |

- 구조화 상태는 **현재 값 + 이전 값 + 출처**를 남겨요. 확정 상태(이과장, t4) / 대체된 값(김대리 → 이과장) / 미확정 사항(일정 변경 최종 승인?) / 유지할 조건(초과 전 서면 승인).
- JSON 형식이 맞아도 내용은 따로 대조해요. Rolling Summary는 처음 빠진 조건이 계속 사라져서 출처를 남겨야 해요.
- 원문 추출 압축은 문장을 다시 쓰지 않고 `[p1] 원문`처럼 ID와 함께 남겨요 → 나중에 원문으로 돌아갈 수 있어요(RAG 9-1 문장 추출과 같은 방식).

```python
def missing_evidence(chosen_ids):
    required = {s["id"] for s in sentences if s["needed"]}
    return sorted(required - set(chosen_ids))       # 필요한데 빠진 것
# 한도만 남길 때 누락: ['p2', 'p3', 'p4']   /   조건까지 남길 때 누락: []
```

- 압축 뒤 확인할 축: 길이(같은 기준) · 사실(현재 값?) · 조건(승인 시점·예외·부정 표현 유지?) · 출처(원문을 다시 찾나?) · 답변.
- 압축률 = 1 − 압축 후 토큰 / 압축 전 토큰. 같은 토크나이저·같은 메시지 구성으로 세고, **높다고 품질이 좋아진 게 아니에요.**

### 4. Map → Reduce (3-2강)

```text
예산 1,500 · 지시 200
요약 9개 한꺼번에: 3,600 + 200 = 3,800 → 초과
첫 번째 Reduce:   요약 3개씩 세 묶음, 묶음마다 1,200 + 200 = 1,400
두 번째 Reduce:   새 요약 400 × 3 + 200 = 1,400
```

- 각 요약에 원문 ID와 적용 범위를 남겨 예외 조항을 다시 연결해요. 빠진 사실은 뒤 단계 요약으로 복구할 수 없어서 숫자·조건은 원문과 대조해요. 길이가 줄지 않거나 반복 상한을 넘으면 중단하고 방식을 바꿔요.

## 질문과 새로 알게 된 점

### q1\_hard: 출력 예약을 64로 줄이면

```python
input_budget = request_limit - output_reserve - margin    # 256 − 64 − 32 = 160
kept = select_recent(turns, input_budget)
used = count_tokens(make_messages(kept))                  # 남은 턴 3, 사용 160
# 담당자 이과장 포함: True / 마감 10월 22일 포함: True
```

- 담당자와 마감일이 들어오지만 대신 답변 공간이 64토큰으로 줄었어요. 답변이 길어지면 잘릴 수 있어서 한도를 늘리는 것과 비교해 봐야 해요.

### `make_messages(kept)`: 리스트 평탄화

```python
history = [message for turn in kept for message in turn]
return [system, *history, question]
```

- `kept`는 턴(= [user, assistant]) 리스트 = **리스트 안의 리스트**. messages는 한 줄 리스트여야 해서 평탄화해요.
- 컴프리헨션의 for 두 개: **앞이 바깥(턴), 뒤가 안쪽(메시지)**. 턴 순서와 턴 안의 user → assistant 순서가 유지돼요.
- `*history`: 리스트를 풀어서 끼워 넣기. `*` 없이 `[system, history, question]`이면 리스트가 통째로 한 칸에 끼어 잘못된 모양이 돼요.

### q2\_hard: 새 변경 기록을 상태에 반영

```python
for event in new_events:
    field = event["field"]
    if field in state:
        replaced.append(state[field])   # ① 옛 값을 먼저 보관
    state[field] = event.copy()         # ② 새 값으로 (없으면 새 칸)
# 담당자: 박부장(t7) · 마감일 2026-10-22(t5) · 예산 1억 2천만원(t6)
# replaced 4개 — 이전 담당자 [('김대리','t1'), ('이과장','t4')]
```

- **순서가 중요:** 옛 값을 replaced로 빼 두고 그다음 덮어써요. 반대면 옛 값을 잃어요.
- **`append`는 복사지 꺼내 가는 게 아님:** append 직후에도 state 칸에는 김대리가 그대로 있고, 다음 줄 `=`가 그 자리를 이과장으로 바로 바꿔요. 칸이 비는 순간은 없어요.
- **왜 덮어써지나:** 딕셔너리는 키 하나에 값 하나. 이미 있는 키에 `d[키] = 값`하면 교체, 없으면 새로 만들어요. "덮어써라" 명령이 따로 있는 게 아니라 **대입 자체가 교체**(`x = "김대리"; x = "이과장"`과 같은 규칙).
- 덮어쓰는 건 `=` 대입이고 `.copy()`가 아니에요. `.copy()`는 state의 dict를 new\_events의 dict와 분리해서, 원본 event를 나중에 고쳐도 state가 안 바뀌게 해요.
- **따옴표 차이:** `event["field"]`는 "field"라는 **글자 키**로 값("담당자")을 꺼내고, `state[field]`는 field **변수의 값**을 키로 써요(= `state["담당자"]`). `state["field"]`로 쓰면 모든 항목이 "field"라는 칸 하나에 덮어써져요(RAG 실습 `"category"` vs `category` 실수와 같음).
