# Context Engineering

> 2026-10-28, Context Engineering 1일차(1~4장 8강) 수업 기록입니다. RAG가 "무엇을 찾을까"였다면, 컨텍스트 엔지니어링은 **"이번 요청에 무엇을, 누구의 것을, 얼마나, 어떤 순서로 넣을까"**입니다.

## 큰 흐름

```text
오전: 무엇을 넣고, 누구의 것을, 언제까지
  1-1 나누기    지시·질문·문서·도구 결과·메모리 → kind / role 분리, [id / kind / source] 표지
  1-2 고르기    범위 → 유효성 → 일관성 → 관련성 → 예산, Skills
  2-1 기억 설계  저장하지 않음 / 현재 대화만 / 확인 필요 / 장기 저장, 조회 시 만료
  2-2 Mem0      저장 → 조회 → (ID로) 수정 → 삭제

오후: 길어지면 줄이고, 섞이면 걸러요
  3-1 세기      토큰 예산 = 한도 − 출력 예약 − 여유분, 최신 턴부터 Sliding Window
  3-2 줄이기    현재 값·이전 값·출처, 원문 추출 압축 → 빠진 근거 확인
  4-1 재사용    고정은 앞 · 요청별은 뒤 → Prefix cache, 서버 지표로 확인
  4-2 거르기    범위 → 본문(의심 문구) → 실행 전 도구 검사
```

한 요청으로 이으면 이렇게 돼요.

```text
사용자·질문 확인 → 허용된 자료·기억만 선택 → 전체 토큰 계산(출력 공간 먼저)
→ 넘치면 조건·출처를 지키며 압축 → 고정 지시는 앞에 일정하게 → 실행 전에 다시 검사
```

## 오늘의 교훈

1. **많이 넣는 게 좋은 컨텍스트가 아니다.** 필요한 정보를, 유효한 범위에서, 예산 안에, 권한에 맞게.
2. **점수보다 권한과 유효성이 먼저다.** 관련성 점수는 걸러진 자료끼리만 비교한다.
3. **길이 통과 ≠ 근거 보존.** 줄인 뒤에는 빠진 조건이 없는지 확인한다(RAG 9-1과 같은 교훈).
4. **ID와 출처로 고정한다.** 검색 순서나 모델의 말 대신, 기록된 ID·출처·서버 지표로 확인한다.

| 3-1 토큰 예산 | 1장 문서 예산, 6-1 문자 예산 |

| 4-2 실행 전 검사 | 6장 `validate_answer`·`bind_claim`, 9-2 인용 검사 |
