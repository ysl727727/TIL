## 오늘 배운 것
- Q·K·V는 같은 입력의 세 관점(찾을 정보 · 비교용 색인 · 실제 내용). Causal mask는 `-inf`로 채워야 한다(0이면 softmax 뒤에도 확률이 남는다).
- Base Model은 "텍스트를 잘 이어 쓰는 모델". 지시를 따르는 능력은 **SFT로 따로 배운 행동**이다.
- SFT는 형식·말투·처리 순서를 잘 바꾸지만, 최신 지식이나 실시간 정보는 RAG·Tool이 맞다.
- Preference data는 `prompt` · `chosen` · `rejected`. RLHF는 순위 → Reward Model → PPO, DPO는 pair로 policy를 직접 학습.
- 평가 rubric을 먼저 만들어야 "그냥 더 좋아 보인다"로 데이터가 흔들리지 않는다. reward hacking 주의.
- Responses API 최소 흐름은 `model + input → output_text`. 운영에서는 `id` · `status` · `usage`도 기록한다.
- 좋은 Developer Prompt = 역할 · 맥락 · 범위 · 제약 · 출력 형식 · 성공 기준을 담은 작은 계약서.

## 왜 중요한가
- "규정 같은 지식은 SFT보다 RAG"라는 기준이 생겼다. 이후 RAG 과목 전체의 출발점.
- API 키는 코드에 넣지 않고 환경 변수·Secrets로 → 이후 모든 API 실습의 전제.

## 코드/예시
```python
request_body = {"model": "gpt-4.1-mini", "input": "HTTP 요청과 응답을 식당 주문에 빗대어 설명해 줘."}
print(json.dumps(request_body, ensure_ascii=False, indent=2))   # 보내기 전에 모양 확인

client = OpenAI(api_key=getpass("OpenAI API 키: ").strip())
response = client.responses.create(
    model=...,
    instructions="처음 배우는 사람에게 한국어로 설명해 줘. 일상적인 예시를 하나 포함한 두 문장으로 답해 줘.",
    input="HTTP가 뭐야?",
)
print(response.output_text)
print(response.to_json())        # id, model, output, usage 원본
```

## 헷갈렸던 부분 & 해결
- `output_text`는 원래 응답에 있는 칸이 아니라 SDK가 `output` 안 텍스트를 모아 주는 편의 속성.
- SDK가 딕셔너리를 JSON으로 바꿔 HTTP 요청을 보내 준다 → 나중에 데이터 엔지니어링 2장(HTTP)에서 같은 일을 직접 했다.
- 3~5장은 이론 PDF 정리이고, 실습은 5장 API 첫 요청만 했다.
