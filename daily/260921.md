## 오늘 배운 것
- 데이터를 찾기 전에 **서비스가 답할 질문**부터 적는다. 값이 자주 바뀌나 / 설명이 필요하나 / 과거와 비교해야 하나.
  - 문맥이 중요 → 공식 문서 + RAG, 현재값 → 질문 시점 API, 과거 비교 → 주기적 스냅샷. 섞어 쓸 수도 있다.
- 수집 경로(파일·공공 API·외부 API·웹)와 데이터 형식(CSV·JSON·HTML·PDF)은 **다른 축**이다.
- 수집 비용은 API 요금만이 아니라 승인 시간, 정리, 구조 변경 대응, 재시도, 저장까지 포함한다.
- 리스크 게이트 5단계: 이용약관 → robots.txt → 개인정보 → 저작권·라이선스 → 접근·부하. 후보를 가능/주의/제외로 나누고 근거와 확인일을 남긴다.
- HTTP: base URL과 endpoint 구분, header(인증·형식) / query(거르기) / body(구조화 입력). API 키는 환경 변수로.
- 응답 검증 순서: `raise_for_status()` → Content-Type → 리스트인지 → 필수 키.
- 3장: `has_next`로 page 반복, 429면 page를 올리지 않고 같은 page 재시도, 목록 병합은 `append` 대신 `extend`, 원본(`raw_response.json`)과 가공(`items.json`/`csv`)을 나눠 저장.

## 왜 중요한가
- "기술적으로 가져올 수 있다"와 "써도 된다"는 별개의 질문이다. 공개 접근 ≠ 저장·가공·배포 허용.
- RAG에 모든 걸 넣는 게 아니다. 빠르게 바뀌는 현재값은 질문할 때 조회하는 게 맞다. 이 구분이 이후 RAG 설계의 출발점이다.

## 코드/예시
```python
def auth_headers():
    key = os.getenv("PRACTICE_API_KEY", "").strip()
    if not key:
        raise RuntimeError("PRACTICE_API_KEY가 비어 있습니다.")
    return {"Authorization": f"Bearer {key}"}

def read_posts(response):
    if "application/json" not in response.headers.get("Content-Type", ""):
        raise ValueError("JSON 응답이 아닙니다.")
    items = response.json()
    if not isinstance(items, list):
        raise ValueError("응답은 글 목록이어야 합니다.")
    for item in items:
        if not isinstance(item, dict) or not {"id", "title", "body"}.issubset(item):
            raise ValueError("글의 필수 필드가 없습니다.")
    return items
```
- 1장 실습: 후보 4건 → 가능 2(교육비 규정 RAG, 잔여석 API) · 주의 1(robots 미확인) · 제외 1(개인정보) → `collection_plan.json`
- 2장 실습: JSONPlaceholder `live` GET 200, 글 2건. `MockTransport`로 인증 헤더 연습(공개 클라이언트에는 키 안 보냄)

## 헷갈렸던 부분 & 해결
- `request_posts`(응답 객체 반환)와 `read_posts`(리스트 반환)를 둘 다 리스트를 준다고 생각하면 `.headers`나 `.json()`에서 오류가 난다.
- 404 JSON은 상태 검사에서, 200인데 객체 하나인 응답은 리스트 검사에서 멈춘다. 같은 실패라도 **멈추는 위치**가 다르다.
- `os.getenv(..., "")` 기본값을 빈 문자열로 두면 변수가 없어도 `.strip()`을 쓸 수 있다.
- 429는 키가 틀린 게 아니다(인증 실패는 401). 빈 `items`가 항상 마지막 페이지도 아니다.
- 일부만 실패했을 때 실제 데이터와 샘플을 섞으면 출처가 섞인다 → 처음부터 다시 받아 통째로 교체.
