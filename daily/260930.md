## 오늘 배운 것
- `prompt | model | parser`는 **연결만** 한다. 실제 API 호출은 `invoke()` 때 일어난다.
- `invoke()`는 1건, `batch()`는 리스트(결과도 입력 순서대로, 입력 수만큼 API 호출), `stream()`은 조각을 반복문으로 받는다.
- 앞 결과가 필요하면 Sequence, 같은 입력을 각자 쓰면 Parallel(모델 branch 수만큼 API 호출).
- `.assign()`은 원본 dict를 그대로 두고 필드를 **추가**한다. 서로 의존하는 필드는 assign을 단계별로 나눈다.
- `with_structured_output()`으로 Pydantic 객체를 받는다. `parser.parse()`는 JSON 해석 → 스키마 검증 두 단계.
- 검증 실패 시 수정 요청은 **최대 1회**, 같은 Parser로 재검증하고 또 실패하면 `None`.
- Document: 본문은 `page_content`(str), 부가 정보는 `metadata`(dict). 같은 의미는 모든 문서에서 같은 키로, 선택 키는 `.get()`으로 읽는다.

## 왜 중요한가
- 체인 오류가 나면 경계 중 어디서 자료형이 바뀌었는지부터 본다: `dict → ChatPromptValue → AIMessage → str`.
- 스키마를 통과했다는 건 **형식**만 맞다는 뜻이지 내용이 정확하다는 뜻이 아니다. 이 생각이 이후 RAG 6장 `validate_answer`까지 이어진다.

## 코드/예시
```text
chain = prompt | model | parser        ← 이 줄에서는 호출 없음
chain.invoke({"question": q})          ← 여기서 1번 호출
chain.batch([{...}, {...}, {...}])     ← 3번 호출, 결과도 3개 (입력 순서)

RunnableParallel(a=chain_a, b=chain_b) ← 같은 입력, 모델 branch 2개면 2번 호출
RunnablePassthrough.assign(x=...)      ← 원본 dict + x
```
- 3~5장은 실습 노트북 없이 이론과 확인 문제만 정리했다.

## 헷갈렸던 부분 & 해결
- `parse()` 실패는 `OutputParserException`, `model_validate()` 실패는 `ValidationError`. 실패한 단계가 다르다.
- `batch()`가 묶어서 1번 호출하는 줄 알았는데 입력 수만큼 호출한다(비용).
- formatter는 Document를 바꾸지 않고 **표시용 문자열**만 만든다.
