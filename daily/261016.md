## 오늘 배운 것
- 내 담당: 커플 16유형 분류 모델(klue/bert-base, 축별)과 LangChain 해설 체인·생성 모델 비교. 결과는 test macro-F1 **0.831** / 정확도 0.858, 해설 규칙 위반 0/24.
- 첫 점수 0.079의 원인은 모델이 아니라 **흔들리는 정답**이었다. 판단 기준을 코드(규칙 라벨러)로 고정하고 판단 재료를 텍스트에 빠짐없이 넣자 데이터를 늘릴수록 점수가 올랐다(0.165 → 0.757).
- 효과 큰 순서: 규칙 라벨 + 데이터 증가 > **어려운 사례 1,200쌍**(0.744 → 0.802) > 축별 분류(0.714 → 0.744).
- 규제를 넣어도 점수가 그대로면 남은 오차는 과적합이 아니다.
- TF-IDF(0.428)는 조각 개수만 세서 "중요도가 같으면 태그로 비교" 같은 조건을 못 따라 한다.
- LLM에 규칙만 설명하면 축별 0.8이어도 네 축을 다 맞혀야 하니 `0.8⁴ ≈ 0.41`. 예시로 배운 BERT는 `0.95⁴ ≈ 0.81`.
- LangChain: `prompt | model | parser`에서 모델 자리만 바꿔 같은 24건·같은 프롬프트로 비교했다.

## 왜 중요한가
- 120쌍 validation 1위가 1,200쌍 dev에서 3위였다. **작은 평가 세트로는 순위를 믿을 수 없다** → dev를 따로 두고 test는 1회만. 이 경험이 RAG 8장 평가를 들을 때 그대로 이어졌다.
- 증상을 막는 장치(재작성)와 원인을 고치는 것(프롬프트)은 다르다. 반대 극 언급 3/24를 재작성으로 막고, 프롬프트에서 원인을 고쳐 첫 초안 0/24 · 비용 −21%.

## 코드/예시
```text
0.079  흔들리는 정답
→ 규칙 라벨러로 정답 고정 + 판단 재료를 텍스트에 다 넣기
→ 데이터 증가 0.165 → 0.757
→ 축별 분류 0.714 → 0.744
→ 어려운 사례 1,200쌍 0.744 → 0.802
→ test 0.831

곱의 함정: 0.8 × 0.8 × 0.8 × 0.8 = 0.41,  0.95⁴ = 0.81
```

## 헷갈렸던 부분 & 해결
- 발표 중 "잠시 후 다시 시도해 주세요" 오류 → 원인은 **같은 IP에서 10분에 분석 5회** 요청 제한이었다. 강의실 와이파이처럼 여러 명이 같은 IP를 쓰는 환경에서는 금방 막힌다. 입력·모델 문제가 아니라 운영 설정 문제.
- 오류 문구 하나로 원인을 좁혔다. 서버 코드에서 같은 문구를 쓰는 곳이 요청 제한 하나뿐이었다.
- 학습률은 작은 차이로 학습 전체를 무너뜨릴 수 있다(5e-5 → 0.041).
- 0.831은 "텍스트만 보고 우리 규칙을 얼마나 따라 하나"이지 실제 궁합 적중률이 아니다.
