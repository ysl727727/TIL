## 오늘 배운 것
- 프롬프트 엔지니어링은 content에 들어갈 **글을 잘 쓰는 것**, 컨텍스트 엔지니어링은 **무엇을 얼마나 넣을지 고르는 것**. RAG 1~9장 대부분이 사실 컨텍스트 엔지니어링이었다.
- 자료 분류 `kind`(document · tool_result · memory)는 앱이, 메시지 역할 `role`(system · user …)은 API가 정한다. 지시는 system, 자료와 질문은 user에 `[id / kind / source]` 표지와 함께.
- 고르는 순서: **접근 범위 → 유효성(현행·만료) → 일관성 → 관련성(점수) → 예산.** 점수 1.00·0.99짜리가 먼저 빠졌다.
- 메모리는 저장 장소가 아니라 쓰임으로 나눈다(지금 작업 = 단기, 다음 세션 = 장기). `decide_memory`가 결정과 이유를 함께 돌려주고, 만료는 조회 시점에 다시 본다.
- Mem0: `from_config`는 빈 저장소 설정, `add`가 기억 넣기. add 응답의 ID로 대상을 고정하고 `owned_record`로 소유자를 확인한 뒤 수정·삭제.
- 토큰 예산 = 한도 − 출력 예약 − 여유분. Qwen3 토크나이저 + chat template로 전체를 세고 최신 턴부터 담는다(256 → 1턴, 512 → 6턴).
- 압축은 현재 값 · 이전 값 · 출처를 남기고, 원문 추출 뒤 `missing_evidence`로 빠진 근거를 확인한다.
- Prompt Cache는 **맨 앞부터 같은 토큰**까지만 재사용 → 고정 지시는 앞, 요청 ID는 뒤(공통 A 11 · B 94 · 정책 변경 8).
- 오염은 범위 → 본문 → 실행 전 도구 검사 순으로 거른다. 문구 필터는 오탐(security-guide)과 미탐(paraphrased-note)이 생긴다.
- Python 보강: 같은 답이라도 입력이 커지면 비용이 다르다. 버블 정렬은 n²(n이 2배면 4배), 이진 탐색은 log₂n(100만 개 → 20번), 전제는 정렬. `bisect_right − bisect_left` = 그 값의 개수.

## 왜 중요한가
- "필요한 정보를, 유효한 범위에서, 예산 안에, 권한에 맞게 넣는다" — RAG에서 따로따로 배운 중복 제거·예산·압축·보류가 한 요청 안에서 어떻게 연결되는지 정리됐다.
- 길이 통과와 근거 보존은 다른 조건이다(256 한도는 들어왔지만 담당자 근거가 없음). RAG 9-1 예산 70과 같은 교훈.

## 헷갈렸던 부분 & 해결
- context(참고 자료라는 종류)와 content(메시지의 칸 이름)는 다른 말이다.
- `isinstance(True, int)`가 True라서 ttl 검사는 `type(ttl) is not int`로. 안 그러면 1일짜리 기억이 조용히 저장된다.
- uuid는 암호화가 아니라 겹치지 않는 이름표일 뿐 → ID만 믿지 말고 `owned_record`로 소유자 확인.
- `state[field]`(변수 값을 키로) vs `state["field"]`(글자 키). 덮어쓰기는 `=` 대입이고 `.copy()`는 원본 event와 분리하는 것.
- `bodies[meta["id"]]`: bodies는 ID → 본문 dict라 그 문서의 ID로 찾는다. 순서 인덱스로 짝을 맞추면 어긋날 때 조용히 틀린다.
- 키트의 grpcio 1.85.0을 Windows 스마트 앱 컨트롤이 막아서 2장 2강만 `uv run --with grpcio==1.84.0`으로 실행했다. `printsection`은 키트에 없어서 `uv add`로 추가.
