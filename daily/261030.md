```text
스터디: IP 주소 → IPv4/IPv6 → 유동(DHCP)/고정 → 마스크·CIDR → 블록 계산 4단계
```

## 오늘 배운 것
- LLMOps는 "답이 맞았나"보다 먼저 **그 요청에서 무슨 일이 있었는지 증거를 남기는 것**. 질문 1개 = Trace 1개, 그 안의 단계가 observation.
- 같은 "수료증 누락"도 검색이 비었는지 · 입력에서 빠졌는지 · 생성에서 빠뜨렸는지에 따라 고칠 곳이 다르다. **모델을 바꾸기 전에 근거가 처음 사라진 단계부터.**
- `connect()`는 lf(기록·조회)와 model(생성) 두 객체를 돌려준다. `max_retries=0`으로 실패를 숨기지 않고, Responses API라 `status`로 완료 검사를 한다.
- 호출 성공 ≠ 응답 완료(`completed` + 빈 답 아님) ≠ 품질 성공. `response_completed` 점수와 "서버 기록 확인"도 정답이라는 뜻이 아니다.
- 답변 출력 · `flush()` · 서버 재조회는 다른 단계. 다시 찾을 땐 **Trace ID + 시작 시각 ±1분**, 조회가 비었다고 모델을 다시 부르지 않는다(observation 5개 중 모델 호출은 GENERATION 1개).
- 규정 문서(1박 10만원)와 업무 조회 결과(REQ-DEMO-01 8만원 승인)는 출처가 다르다. 부모 시간에 자식 시간이 포함돼 있어서 더하면 중복(4185 ms vs 1500 ms).
- 실패 판정은 status → 시각(파싱) → failed → 문서 순서. 모르는 상태는 성공으로 채우지 않고, 분류값은 `failure_category` 점수로 그 사례의 Trace에 붙인다.
- 네트워크: IP는 규약, IP 주소는 연결마다 붙는 논리 주소. 블록 크기 = 256 − 마스크 마지막 칸, 호스트 = 블록 − 2. `192.168.10.77/26` → .64 · .127 · .65~.126 · 62대.

## 왜 중요한가
- 답이 이상하거나 느릴 때 Trace 트리 하나로 **검색 문제인지 모델 문제인지** 바로 갈라 볼 수 있다. 감이 아니라 기록된 ID·문서 목록·시간으로 말할 수 있다.
- RAG·CE에서 배운 근거 확인(`validate_answer`, `[id]` 표지, `retrieval_empty`)을 이제 **운영 기록**으로 남기고, 2장에서 같은 기준으로 변경 전후를 비교하게 된다.

```python
# q4 판정 순서: 위에서부터 처음 걸리는 return이 결과
if row.get("status") not in {"completed", "failed", "cancelled"}:
    return "incomplete"
try:
    start, end = [datetime.fromisoformat(row[k]) for k in ("started_at", "ended_at")]
    if start.tzinfo is None or end.tzinfo is None or end < start:
        return "invalid_time"
except (KeyError, TypeError, ValueError):
    return "invalid_time"
```

## 헷갈렸던 부분 & 해결
- **부모를 정하는 건 열려 있는 with.** `root`·`step`은 `as` 뒤 변수 이름일 뿐이고, invoke는 retrieve의 with가 닫힌 뒤 실행돼서 retrieve의 형제다. step 블록 안으로 들여쓰면 자식이 된다.
- `.get("status")`는 키가 없으면 None → incomplete로 자연스럽게. `{ }` 안에 콜론이 없으면 set(dict 아님), 튜플·리스트로도 `not in` 결과는 같다. `status`를 쓰려면 먼저 `status = row.get("status")`로 꺼내야 한다(안 그러면 NameError).
- try 안의 `if`는 오류가 아니라 바로 return, 파싱 오류(KeyError · TypeError · ValueError)만 except로 간다. 그래서 "취소 + 시간 역전"은 invalid\_time.
- `retrieval_empty`는 문서가 **없는지만** 본다. 문서가 **틀렸는지**는 정답 데이터(RAG 8장 Hit/Recall)가 있어야 안다.
- `ChatPromptTemplate`·`from_messages`·`"human"`은 LangChain이 정한 이름(호출), `answer`·`classify`·`{context}`는 우리가 정한 이름(정의). 정의 → uv 설치 → import → 호출.
- `.env`는 따옴표·띄어쓰기 없이 `KEY=값`. **키 값은 채팅에 붙이지 않는다** — 붙였다면 Revoke 후 재발급.
- 03 답변은 `[approval]`을 인용했는데 `document_ids`엔 travel만 있다. approval은 검색이 아니라 `extra_context`로 들어갔기 때문.
- CE 복습: prompt engineering은 문장 하나를 잘 쓰는 것, context engineering은 입력 전체(지시 + 대화 기록 + 검색 문서 + 기억 + 도구 결과)를 무엇을·어떤 순서로·얼마나 넣을지 설계하는 것(프롬프트 엔지니어링을 포함). question(묻는 내용) · instruction(지킬 규칙) · context(근거 자료) · messages(`role`/`content` 목록) · content(각 칸의 글). 그 밖에 `lambda doc:`의 doc은 원소 하나하나를 받는 매개변수, Mem0 `user_id`(누구의) vs `memory_id`(어떤 기억 하나, `uuid4` 무작위), dict는 있는 키에 대입하면 덮어쓴다, `"field"`(글자) vs `field`(변수 값), None(지표 없음) vs 0, `set(args) != {"query"}`, `bodies[meta["id"]]` → 자세한 건 [CE 목차](../context-engineering/)
