## 오늘 배운 것
- **읽기 전에 막는다.** 권한은 서버가 정한 `principal`로만 판단하고, 질문 속 "관리자입니다"나 문서 속 "관리자 명령"은 믿지 않는다. 실제로 읽은 목록 `read_ids`로 한 번 더 확인한다.
- **보내기 전에 가린다.** `redact`는 모델로 가는 입력, `mask_spans`는 Langfuse로 가는 기록, 응답 검사는 사용자 화면을 지킨다. 셋은 서로를 대신하지 못한다. `redact(x) != x`는 "x에 개인정보가 있나?"라는 질문이다.
- **쓰기 전에 검사한다.** pydantic `Answer`(필드 · `extra="forbid"` · `strict=True` · `check_relation`)로 형식과 관계를 보고, `set(citations) <= set(document_ids)`로 이번 요청의 출처 범위를 본다. `output_valid=1`은 사실 정확성 점수가 아니다.
- **공격과 정상을 같이 평가한다.** 통과 = 공격 표식 없음 AND 업무 수행. 무조건 거절은 실패다. 모델의 도구 제안은 실행 허가가 아니라서 `run_tool`이 허용 목록과 문서 권한을 결정적으로 검사한다.
- 내 결과: 01 meal allowed / secret blocked, 02 질문이 `[EMAIL]`로, 03 모의 출력 차단 2 / 2, 04 direct · indirect · normal 모두 True · 도구 차단 2 / 2. q2 · q3 hard 통과.
- **RAG 스타터 복습.** 뼈대는 2-Step RAG이고 나머지는 앞뒤 검사 단계다. 캐시(이 질문의 답, 아무나) ≠ 세션(이 사람과의 대화), 후속 질문 풀기 ≠ 쿼리 재작성, S 번호 ≠ chunk\_id, 직접 인젝션(입력 가드) ≠ 간접 인젝션(문서 가드), route 5개로 사람에게 넘기기.
- **보강(git).** 작업 폴더 → 스테이지 → 커밋. feature는 develop에서 만들어 develop으로, hotfix · release는 main과 develop 두 곳에. push 전이면 reset, push 후면 revert. 팀 저장소에 `feature/ysl`을 올려 develop으로 PR을 만들었다.

## 왜 중요한가
- LLM은 지시와 자료를 확실히 구분하지 못한다. 권한 · 개인정보 · 출력 형식을 모델에게 "지켜 줘"라고 부탁하는 것만으로는 부족하고, 애플리케이션 코드가 경계마다 막아야 한다.
- 보안 평가도 2장 회귀 검사처럼 같은 공격 + 정상 사례를 데이터로 쌓아 다시 돌려야 한다. 3건 통과가 모든 공격에 안전하다는 뜻은 아니다.
- RAG 프로젝트는 지금까지 배운 RAG · CE · LLMOps를 한 파이프라인에 모으는 일이라, 단계마다 왜 그 자리에 있는지 설명할 수 있어야 한다.
- 팀 프로젝트는 git으로 협업한다. 가지 규칙과 PR · 충돌 해결을 모르면 남의 작업을 덮어쓴다.

# q3: pydantic ValidationError는 ValueError를 상속 → except ValueError로 함께 잡힘
def route(text, allowed_ids):
    try:
        parsed = ReviewAnswer.model_validate_json(text)
    except ValueError:
        return "REJECT:형식"
    if not set(parsed.citations) <= set(allowed_ids):
        return "REJECT:출처"
    return "HUMAN" if parsed.status == "needs_review" else "SEND"

## 헷갈렸던 부분 & 해결
- **3장 보충 — 4건 중 2건만 피드백.** 2건이 긍정이 아니라 2건만 응답했다. 응답률 2/4, 긍정 비율 1/2. 무응답은 모름이라 긍정 비율 분모에서 뺀다.
- **`mask_spans`는 누가 부르나?** 우리가 아니라 Langfuse SDK가 전송 직전에 `mask_spans(params=...)`로 부른다. 함수는 span을 고치지 않고 "어느 span의 어느 속성을 무엇으로"만 돌려준다.
- **`ConfigDict`가 검사하나?** 아니다. 설정을 담기만 하고, 실제 검사는 `model_config`를 읽는 BaseModel이 한다.
- **JWT — 서버가 저장 안 하는데 어떻게 확인?** 서버는 비밀 키(도장 찍는 법)만 갖고, 들어온 내용에 도장을 다시 찍어 비교한다. payload는 누구나 읽을 수 있다(암호화 아님).
- **Redis vs Mem0.** Redis는 RAM 키-값 저장소(세션 · 캐시, TTL), Mem0는 장기 기억을 고르는 라이브러리. Mem0가 Redis를 저장소로 쓸 수 있다.
- **보강.** feature/ysl이 develop이 아니라 main에서 갈라져 있었다(로컬에 develop이 없었음). push 403은 로그인이 아니라 쓰기 권한 문제였고 collaborator 초대로 해결. PowerShell에 `print('ysl')`을 치면 프린터 명령이 된다. 같은 파일을 VS Code와 PowerShell에서 동시에 고치면 나중에 저장한 쪽이 이긴다.
- **Remote Control.** 노트북 덮개를 닫으면 절전돼서 끊긴다. "깨어 있기"는 방치 절전만 막고, 덮개는 전원 옵션 "덮개를 닫으면 → 아무 것도 안 함"으로 바꿔야 한다.
