## 큰 흐름
```text
과제 복습:  RAG(RRF · 별칭 질문 변환) → CE(토큰 예산 창 · 멱등 요약 · 메모리 CRUD) → LLMOps(마스킹 한계 · 평가 단계)

            → 두 번 토큰화 299 / 376 → 답변 77 → −100 마스킹(SFT · DPO 공통) → DPO [chosen, rejected] 인덱스 0 · 1
원칙:       "돌아간다" ≠ "맞다". 무엇을 보장하고 무엇을 보장하지 않는지 구분한다.
```

## 오늘 배운 것
- **RRF는 점수가 아니라 순위를 합친다.** 코사인(0\~1)과 단어 개수(정수)는 척도가 달라 바로 더할 수 없음 → 순위로 바꾸면 키워드 쪽이 BM25든 단어 세기든 계산이 같다.
- **별칭은 검색용 질문만 바꾼다.** `rewrite_query`로 정식 명칭 질문을 만들어 검색하고, 답변 생성에는 원래 질문 + 별칭 사전을 넘긴다.
- **대화 창은 턴 수가 아니라 토큰 예산.** 최근 턴부터 거꾸로 붙이다 예산을 넘으면 `break`, 빠진 턴의 사실은 요약이 최신 값 + 출처 턴 ID로 지킨다.
- **멱등성.** 같은 턴을 두 번 넣어도 결과가 같아야 함 → `processed_ids`로 건너뛰기, 값이 같으면 `changes`에 안 넣음.
- **마스킹 검사 통과 ≠ 개인정보 없음.** 정규식에 안 맞는 연락처는 원문 그대로 모든 기록에 남는다.
- **평가는 단계적으로 섞는다.** 규칙 검사 → LLM-as-judge → 사람 평가 → 운영 피드백. `status="ok"`여도 `passed=False`일 수 있다.
- **파인튜닝 1-2는 두 부분.** 토큰(템플릿 · BPE · MAX\_LENGTH)은 1장 추론부터 7장 API까지 공통, softmax → −log p → p − y는 SFT 손실(3 · 4 · 5장 동일).
- **2장 72개 = 12그룹 × 6유형.** 그룹 = 팀 하나의 숙박 규정(v1 + 개정 v2), 유형 = below · boundary · over\_limit · updated · missing · irrelevant.
- **답변 위치는 두 번 토큰화로 찾는다.** prompt 299 / full 376 → 답변 77(모범답안 75 + `<|im_end|>` + 줄바꿈).
- **−100 마스킹은 SFT · DPO 공통.** DPO도 chosen · rejected 각각 프롬프트는 −100, 답 + EOS만 남긴다. 남긴 토큰으로 하는 일만 다름(평균 손실 vs 응답별 합).

## 왜 중요한가
- 과제 코드가 "돌아간다"와 "맞다"는 다르다. 검색 점수는 올랐지만 Recall은 그대로였고, 마스킹 검사는 통과해도 패턴 밖 개인정보는 남는다.
- 검사가 **무엇을 보장하는지**를 말할 수 있어야 결과를 정직하게 보고할 수 있다(문구 검사 · 정규식 검사 · 세 관문 모두 같은 원리).
- 재시도 · 재실행이 잦은 실무에서는 멱등성이 없으면 같은 사실이 중복 저장되고 변경 이력이 오염된다.
- 학습 데이터의 메타데이터를 모델 입력에 섞으면 정답 누수, 마스킹 경계가 어긋나면 질문 일부를 정답으로 학습 → 둘 다 점수는 좋아 보이는데 모델은 틀린 것을 배운다.

## 헷갈렸던 부분 & 해결

### RAG
- **Dense 검색만 있는데 RRF는 어떻게? (BM25 없음)** 키워드 검색은 `main.py`가 아니라 `support.py`의 challenge 단계에 있음. "VPN" · "승인" · "요청"이 본문에 몇 번 나오는지 세서 정렬하는 단순한 방식(BM25 아님). RRF는 순위만 쓰므로 키워드 순위가 어디서 왔든 계산이 같다.
- **정식 명칭과 별칭이 다르면?** 임베딩 모델은 사내 별칭("초록문" = VPN 원격 접속)을 모름 → 별칭으로 검색하면 벡터가 멀어진다.
  - `rewrite_query`: `aliases.json`으로 별칭을 정식 명칭으로 바꾼 질문으로 **검색**
  - `answer_question`: 생성에는 **원래 질문** + 시스템 프롬프트에 별칭 사전
  - `evaluate`: 문서 · `top_k=1` 고정, 검색용 질문만 바꿔 비교 → 차이 = 질문 변환 효과
  - 결과: 토큰 발급처 0.79 → 0.94, 만료 기간 0.80 → 0.93. Recall · 답변은 전후 모두 1.0이라 **품질 개선까지는 확인 못 함**
  - 한계: 사전에 없는 별칭 · 띄어쓰기 변형 못 잡음, 단순 치환이라 다른 단어 일부까지 바뀔 수 있음, 조사 어긋남("API 토큰를")

### Context Engineering
- **대화가 얼마나 길어지면 예전 말이 지워지나?** 턴 수가 아니라 토큰 예산. `select_window`가 최근 턴부터 거꾸로 붙이며 전체 입력 토큰을 세다 넘는 순간 `break` → 그보다 오래된 턴은 전부 빠짐. 턴 단위라 user · assistant는 같이 남거나 같이 빠짐. 빠진 턴의 사실(담당자 · 마감일 · 승인 조건)은 `summarize`가 최신 값 + 출처 턴 ID로 유지.
- **같은 대화가 두 번 처리되면 중복 저장되나?** 안 됨(멱등성). `merge_summary`는 `processed_ids`에 있는 턴을 `continue`, 사실이 없던 턴도 ID는 기록, 새 턴이라도 값이 같으면 `changes`에 안 넣고 출처만 최신 턴으로. `checks.py` replay 검사가 같은 턴 재투입 결과가 완전히 같은지 확인.
- **"Mem0 같은 메모리 저장소로 단기 · 장기 메모리 CRUD"는 과제의 어디?** `memory_action`(생성 · 조회 · 수정 · 삭제). 단기 = 세션 안에서만, 장기 = `memory.json`에 저장되어 다음 대화에서도 조회. `user_id`별 분리와 잘못된 작업 차단도 검사.
  - `select_context`: user · trusted · active · 만료 여부로 거른 뒤 priority 순 정렬
  - `build_messages`: 지시(developer) · 참고 자료 · 대화 기록 · 질문 역할 분리
  - `cache_key`: `sha256(user_id + "\n" + prefix)`. 정적 prefix를 앞에 고정하면 프롬프트 캐시가 잘 맞음

### LLMOps
- **이메일 · 전화번호가 마스킹 패턴에 안 맞으면?** 그대로 기록된다. `mask_text`는 정규식 `sub`라 안 맞으면 오류 · 경고 없이 원문 반환. 마스킹이 모델 입력 · Langfuse 관측 기록 · 모델 출력 · 최종 답변에 모두 적용되므로 패턴을 벗어나면 **모든 곳에 원문이 남는다.** `masked` 검사도 같은 정규식이라 보장 범위는 "패턴에 맞는 연락처가 남지 않았다"까지. 실무 보완: 패턴 넓히기 · 전용 개인정보 탐지 도구 · 원문 수집 자체를 줄이기.
- **실무에서는 사람이 평가하나? (과제는 문구 검사)** 단계적으로 섞는다.
  1. 규칙 기반 자동 검사(`must_include` · `must_not_include`): 빠르고 결과가 매번 같아 회귀 테스트에 적합
  2. LLM-as-judge: 의미가 맞는지 판단
  3. 사람 평가: 기준 만들기 · 자동 평가 검증 · 위험하거나 애매한 사례 · 배포 전 최종 확인
  4. 운영 피드백: 실제 사용자 반응
  - 문구 검사 약점: 같은 뜻을 다르게 쓴 정답을 떨어뜨림, 필수 문구만 넣은 틀린 답을 통과시킴
  - 과제 결과: baseline 2/4(unknown · direct가 validate 실패), candidate 4/4 → `decide_rollout` approve=True

### 파인튜닝 (역량 목록 + 1\~7장 복습 질문)
- **학습 데이터 준비 = 학습 전 데이터 정제.** instruction 또는 chat(messages) 형식 통일, 중복 제거, 품질 검수(QA), train / validation / test 분리.
- **Chat Template.** `tokenizer.apply_chat_template(messages)`가 role별 메시지를 모델이 학습한 특수 토큰 형식 문자열 하나로 바꿈. 모델마다 다르므로 학습과 추론에 **같은 템플릿**.
- **Loss Masking.** system · user · 템플릿 머리말은 `labels = -100`(CrossEntropyLoss가 무시), **assistant 답변부터 EOS까지만** 손실. EOS까지 넣는 이유 = 언제 멈출지 배워야 함(빠지면 끝없이 생성). 템플릿 토큰(`<|im_start|>assistant`)이 있어야 답변 시작 위치를 찾으므로 템플릿과 마스킹은 함께 간다. TRL `SFTConfig`의 `assistant_only_loss` · `completion_only_loss`(예전엔 `DataCollatorForCompletionOnlyLM`)가 이 일을 하는데 버전마다 이름 · 동작이 달라 문서 확인 필요.
- **1-2 토큰 · 원리는 SFT 기준인가?** 반만 맞음.
  - 토큰 부분(`apply_chat_template` · byte-level BPE · 숫자 한 자리씩 · MAX\_LENGTH 512)은 1장 추론 · 2장 검증 · 3장 SFT · 6장 DPO · 7장 API 공통
  - `add_generation_prompt`도 기준은 SFT가 아니라 "생성하느냐(True) / 정답이 이미 들어 있느냐(False)"
  - softmax → −log p → p − y는 SFT 손실. 4장 LoRA · 5장 QLoRA도 같은 손실이고 움직이는 파라미터만 다름
  - 6장 DPO는 CE로 토큰 log p를 꺼내는 데까지만 공유, 이후 합 → reference 차 → β · margin → −log σ라 기울기가 p − y가 아님
  - "세 점수" 예제는 정답 칸 하나인 일반 분류 예제 → 이 계산을 답변 토큰 위치마다 반복하면 SFT
- **12 × 6유형이 boundary 그거? 12그룹은?**
  - 6유형 = 1장 네 문항(boundary · over\_limit · updated · missing) + 2장에서 추가한 below(한도 −5,000) · irrelevant(무관한 숙박 문서, missing과 같은 질문)
  - 12그룹 = 팀 12개의 숙박 규정(`policy01`\~`policy12`). 그룹마다 `limit` 65,000\~120,000원, `updated_limit` = limit + 10,000, 문서 v1 · v2. 예: policy03 다온 85,000 → below 80,000 · boundary 85,000 · over\_limit 90,000
  - 한 그룹 안에 질문 문장이 같은 쌍 2개(over\_limit ↔ updated, missing ↔ irrelevant) → 행 단위로 섞으면 test 12행 모두 형제가 train에 있고 5행은 질문까지 같음(누수) → 그룹째 8 / 2 / 2 분할: train 48(policy03 · 04 · 06 · 07 · 08 · 09 · 10 · 12) · dev 12(01 가온 · 05 마루) · test 12(02 · 11)
- **"메타데이터 vs messages, 두 번 토큰화 299 / 376 → 답변 77"은 무슨 뜻?** 위 코드/예시 참고. 메타데이터 = 송장(분리 · 집계용), messages = 상자 안 내용물(모델 입력). 두 번 토큰화 길이 차이로 정답 시작 인덱스(299)를 찾고 앞부분을 −100으로 가림. 길이는 문항마다 257(missing, 문서 없음)\~380, 모두 512 이하.
- **왜 "vs"라고 썼나?** 비교가 아니라 한 레코드 안의 **역할 구분**이라 "메타데이터(분리 · 집계용) / messages(모델 입력)"가 맞는 표기. 1-1의 `cases`(모델) / `review_criteria`(사람)도 같은 뜻. 5-3 LoRA · QLoRA 메모리 비교 같은 자리만 진짜 vs.
- **`dpo_terms`의 `rewards[0]`, `rewards[1]`은?** 주석 `[chosen, rejected]` 순서 그대로 0 = chosen, 1 = rejected. margin = chosen이 학습 전보다 오른 양 − rejected가 오른 양. 데이터를 이 순서로 쌓았기 때문에 의미가 생기고, 순서가 뒤집히면 margin 부호가 바뀌어 나쁜 답을 선호하도록 학습된다.
- **system · user 빼고 assistant + EOS만 보는 건 SFT에만 있나?** DPO에도 있다. 6장 `encode_response`도 두 번 토큰화 + 경계 assert → 프롬프트 −100, 답 + EOS만 남김(EOS 뒤 템플릿 개행은 버림). chosen · rejected를 [2, T]로 패딩(input\_ids = pad ID · attention\_mask = 0 · labels = −100). `response_logps`의 `mask = targets.ne(-100)`이 "답 + EOS 칸 고르기". 차이는 남긴 토큰으로 SFT는 −log p **평균**, DPO는 log p 응답별 **합** → reference 차 → margin.
