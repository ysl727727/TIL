## Core Theory

### 1. 질문에서 시작하기 (1-1강)

데이터를 찾기 전에 서비스가 답해야 할 질문부터 적는다. 같은 주제라도 필요한 데이터가 다르다.

| 질문 | 중요한 것 | 어울리는 출발점 |
| --- | --- | --- |
| 현재 대여 가능 수는 몇 대인가? | 지금의 값 | 질문 시점 API |
| 대여 규정은 무엇인가? | 근거 문장과 설명 | 공식 문서 |
| 지난달 이용량은 어떻게 변했는가? | 과거 시점별 값 | 저장 파일 또는 스냅샷 |

질문 옆에 **값이 자주 바뀌는가 / 앞뒤 설명이 필요한가 / 과거와 비교해야 하는가** 세 가지를 표시하면 후보를 빠르게 좁힐 수 있다. "어디서 가져올까?"보다 "어떤 상태의 데이터가 필요한가?"가 먼저다.

### 2. 수집 경로와 데이터 형식은 다른 축

- **수집 경로(access path)**: 정적 파일 / 공공데이터 API / 외부 서비스 API / 웹 데이터 수집
- **데이터 형식(representation)**: CSV / JSON / HTML / PDF·Markdown

둘은 조합 가능하다(예: 공공 API가 JSON을 반환). "CSV와 API 중 무엇이 좋은가?"는 두 축을 섞은 질문이며, ① 어떤 경로가 목적과 시점에 맞는가 → ② 그 경로가 제공하는 어떤 형식을 쓸 것인가 순으로 생각한다.

다섯 후보의 특징:

- **정적 파일**: 한 번에 많은 행을 받기 편하지만 새 파일이 나오기 전까지 값이 갱신되지 않는다.
- **CSV**: 단순한 표·통계에 맞고 열 이름·인코딩·빈 값을 먼저 확인한다. **JSON**: API 응답·중첩 데이터에 맞고 키 이름·배열 위치·자료형을 먼저 확인한다.
- **공공데이터 API**: 조건을 넣어 필요한 범위만 받을 수 있지만 활용 신청·인증 키·호출 한도가 있을 수 있고, "응답을 받은 시각"과 "데이터가 관측된 시각"이 다를 수 있다.
- **외부 서비스 API**: 직접 만들기 어려운 기능을 빠르게 쓰지만 무료 한도·초과 비용·가격 정책 변경에 주의한다.
- **웹 데이터 수집**: 파일·API로 제공되지 않는 설명을 얻을 수 있지만 화면 구조 변경에 취약하고 약관·robots.txt·개인정보·저작권을 먼저 확인해야 한다. "마지막 수단"으로 단정할 필요는 없지만, 더 안정적인 공식 파일이나 API가 있다면 먼저 비교한다.

### 3. 갱신 주기와 수집 비용

갱신 주기는 데이터가 새 값으로 바뀌는 간격이다. 값이 자주 바뀐다고 무조건 API를 써야 하는 것은 아니며, 사용자가 매월 한 번만 본다면 월별 파일로 충분할 수 있다.

수집 비용은 API 요금만이 아니다 — 활용 신청·승인 시간, 정리·오류 확인 시간, 웹 구조 변경 대응 유지보수, 호출 실패 재시도, 저장 공간과 백업 비용이 모두 포함된다. 입문 단계의 원칙 질문: *"이 경로를 한 달 동안 운영할 때 사람이 반복해서 해야 할 일은 무엇인가?"*

### 4. RAG / 질문 시점 API / 스냅샷 선택

- 신청 자격, 취소 규정, 용어의 정의처럼 **문맥이 중요한 질문** → 공식 문서와 RAG
- 지금 대여 가능한가, 오늘 대기질은 어떤가처럼 **현재값이 중요한 질문** → 질문 시점 API
- 지난주와 이번 주 비교처럼 **과거 시점이 필요한 질문** → 주기적 스냅샷(특정 시점의 응답을 파일로 남기는 것)

현재값 API가 과거까지 제공한다고 가정하면 안 된다. 혼합형도 가능하다 — 정책 설명은 RAG, 오늘의 값은 API 조회.

Python 판단 규칙(정답표가 아니라 첫 후보를 좁히는 학습 도구):

```python
def recommend_path(need):
    if need["needs_history"]:     return "주기적 파일/스냅샷"
    if need["changes_often"]:     return "질문 시점 API"
    if need["needs_explanation"]: return "공식 문서/RAG"
    return "정적 파일"
```

과거 비교는 현재값만으로 복원할 수 없으므로 `needs_history`를 `changes_often`보다 먼저 본다.

### 5. 선택 기준표

선택 기준표는 정답표가 아니라 **근거를 보이게 하는 표**다: 목적 적합성(대표 질문에 필요한 값이나 설명이 있는가) / 갱신성(질문에 필요한 시점과 갱신 주기가 맞는가) / 구조(필드나 문서 구조를 이해할 수 있는가) / 비용(호출료와 관리 시간을 감당할 수 있는가) / 재현성(같은 원본을 다시 확인할 수 있는가) / 이용 가능성(계획한 저장·가공·제공이 조건과 맞는가).

### 6. 기술적 접근과 이용 가능성 구분하기 (1-2강)

브라우저에서 페이지가 열린다고 해서 모든 자동 수집과 재사용이 허용되는 것은 아니다. 반대로 robots.txt에서 허용되어 보인다고 저작권과 개인정보 문제가 모두 해결되는 것도 아니다.

| 질문 | 뜻 |
| --- | --- |
| 접근 가능한가? | 기술적으로 요청하고 응답받을 수 있는가? |
| 자동 수집해도 되는가? | 약관과 운영 정책에 맞는가? |
| 저장해도 되는가? | 개인정보·보관 조건과 맞는가? |
| 가공/공유해도 되는가? | 라이선스와 사용 목적에 맞는가? |

이 중 하나를 확인하고 전체를 가능으로 결론 내리지 않는다.

### 7. 수집 전 5단계 리스크 게이트

**① 이용약관 → ② robots.txt → ③ 개인정보 → ④ 저작권·라이선스 → ⑤ 접근·부하** 순서로 확인한다.

체크 결과의 의미 — `예`: 확인한 근거 URL과 확인일을 함께 기록 / `아니요`: 수집하지 않는 쪽으로 우선 판단 / `불명확`: 임의로 "예"로 바꾸지 않고 문의 대상으로 남김.

**robots.txt 바르게 이해하기**: 접근 통제나 비밀번호 장치가 아니며, Allow 표시가 저작권 이용허락을 뜻하지도 않는다. robots.txt에 없다는 이유만으로 약관 확인을 생략하지 않는다. scheme·host·port가 다르면 적용 대상도 달라질 수 있고, `Crawl-delay`는 RFC 9309 표준 규칙이 아니므로 제공자 문서를 따른다.

**개인정보 가능성**: 이름 한 칸에만 존재하는 것이 아니라 여러 정보가 결합되어 개인을 알아볼 수 있으면 주의가 필요하다. 멈춤 기준 — 공개된 개인 연락처를 대량으로 모은다 / 원래 목적과 다른 용도로 쓴다 / 필요한 기간과 삭제 기준을 설명할 수 없다 / 개인을 알아볼 필요가 없는데 식별자를 그대로 저장한다 / 민감한 내용이 포함될 수 있다. **최소 수집 원칙**: "나중에 쓸지도 모른다"는 이유로 모든 필드를 저장하지 않는다.

**저작권·라이선스**: 무료로 볼 수 있다는 사실과 자유롭게 복제·가공·배포할 수 있다는 사실은 다르다. 라이선스 표시가 있으면 이름만 적지 말고 버전과 원본 URL을 기록한다(`CC BY 4.0`과 `CC BY-NC 4.0`은 조건이 다르다). 표시가 없을 때는 "자유 이용"으로 해석하지 않고, 이용하지 않기 / 링크만 제공 / 권리자에게 문의 / 대체 자료 찾기를 검토한다.

### 8. 가능/주의/제외 판단과 출처 기록

| 상태 | 의미 | 다음 행동 |
| --- | --- | --- |
| 가능 | 확인한 범위에서 계획과 조건이 맞음 | 작은 표본부터 검증 |
| 주의 | 확인하지 못한 항목이나 조건이 있음 | 문의·검토 후 재판단 |
| 제외 | 목적상 불필요한 개인정보 등 뚜렷한 중단 사유 | 수집하지 않고 대안 탐색 |

`가능`은 영구 보증이 아니다 — 수집 범위나 이용 목적이 바뀌면 다시 확인한다.

출처 기록은 데이터의 '영수증'이다. 최소 항목: `source_name`, `source_url`, `checked_at`, `collected_at`(아직 수집 전이면 `None`), `terms_url`, `review_note`. 가공 파일 → 원천 스냅샷 → 수집 시점 → 원문 URL과 이용조건으로 역방향 추적할 수 있어야, 문제가 생겼을 때 "이 데이터는 어디서 왔는가"에 답할 수 있다.

### 9. Playwright 등 브라우저 자동화 선택 기준

일부 웹페이지는 JavaScript가 실행된 뒤에야 내용이 나타나며 Playwright 같은 도구로 다룰 수 있지만, 이 과정의 필수 구현은 아니다. 도구 선택 전에 확인: 공식 파일/API가 정말 없는가 / 약관과 robots.txt를 확인했는가 / 로그인·접근 통제를 우회하지 않는가 / 브라우저 실행 비용을 감당할 수 있는가 / 화면 구조 변경을 어떻게 발견할 것인가. 동적 페이지라는 이유만으로 브라우저 자동화를 바로 선택하지 않는다.

## Questions and Newly Learned Points

- 수집 경로와 데이터 형식은 1:1로 고정되어 있지 않다 — 같은 경로가 여러 형식을, 같은 형식도 여러 경로에서 나올 수 있다.
- 5단계 리스크 게이트의 순서는 **이용약관 → robots.txt → 개인정보 → 저작권·라이선스 → 접근·부하**다.
- 자주 하는 오해 정리: "API가 항상 파일보다 최신이다"(API도 오래된 원천을 제공할 수 있다) / "공공데이터는 품질 검사가 필요 없다"(누락·제공 지연·필드 변경이 생길 수 있다) / "RAG에는 모든 데이터를 넣어야 한다"(빠르게 바뀌는 현재값은 질문 시점 조회가 더 적합) / "JSON이면 정제할 필요가 없다"(필드 누락·자료형 불일치·중복이 있을 수 있다) / "인터넷에 공개되면 자유롭게 학습 데이터로 써도 된다"(공개 접근과 저장·가공·배포 허용은 다르다).
