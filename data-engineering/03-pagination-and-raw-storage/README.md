## Core Theory

### 1. 한 번의 호출로 데이터가 모두 오지 않는 이유 (3-1강)

서버가 수만 건을 한 번에 보내면 응답이 커지고 처리 시간이 길어진다. 그래서 많은 API는 전체 결과를 여러 페이지로 나누며, 이를 **페이지네이션(pagination)**이라고 한다.

페이지네이션의 핵심은 단순하다 — **한 페이지를 성공적으로 받은 뒤 page 번호를 올리고, 마지막이라는 신호가 오면 멈춘다.**

페이지마다 확인할 것: 요청한 page 번호 / 응답 상태 코드 / `items` 배열의 건수 / 다음 페이지가 있는지 알려 주는 값 / 오류가 났을 때 어느 page였는지.

### 2. page와 page_size

```python
page = 1        # 어떤 API는 0부터, 어떤 API는 1부터 시작 — 문서에서 확인
page_size = 2   # API 문서가 허용하는 한 페이지 최대 건수 안에서 선택
params = {"category": "news", "page": page, "page_size": page_size}
```

`page_size` 대신 `size`, `limit`, `per_page`, `numOfRows` 같은 이름을 쓰는 API도 있으므로 문서의 정확한 이름을 사용한다. 최댓값이 있을 수 있으며, 최대가 100인데 1000을 보내면 400 오류가 나거나 서버가 자동으로 100으로 줄일 수 있다.

### 3. 마지막 페이지 신호 세 가지

- **`has_next`**: `{"items": [...], "has_next": False}` — `False`면 반복을 멈춘다.
- **전체 페이지 수**: `{"page": 3, "total_pages": 3, ...}` — 현재 page가 `total_pages`와 같으면 마지막이다.
- **빈 배열**: `{"items": []}` — 다음 페이지의 `items`가 비면 멈추는 API도 있지만, 빈 배열이 일시적인 필터 결과인지 마지막 신호인지 문서에서 확인해야 한다.

근거 없이 섞지 않고 그 API에서 한 가지 규칙을 선택한다. 실습에서는 가장 읽기 쉬운 `has_next` 방식을 사용한다.

### 4. 수집 범위를 먼저 정하기

반복문을 쓰기 전에 목적 / 기간 / 검색 조건 / 시작 page / `page_size` / 최대 page(안전장치) / 마지막 신호를 표로 정해 둔다.

**한 번의 수집 실행에서는 검색 조건과 `page_size`를 고정한다** — 1페이지는 뉴스, 2페이지는 공지처럼 조건이 바뀌면 하나의 연속된 결과가 아니며, 중간에 `page_size`를 바꾸면 서버의 페이지 경계가 달라져 중복이나 누락이 생길 수 있다.

### 5. page 반복 수집 알고리즘

① `page = 1`로 시작 ② 현재 page를 요청 ③ 성공하면 `items`를 전체 목록에 붙임 ④ 마지막 페이지면 멈춤 ⑤ 마지막이 아니면 page를 1 올림 ⑥ ②번으로 돌아감.

```python
collected.extend(page_items)   # 각 항목을 전체 목록 뒤에 이어 붙임
nested.append(page_items)      # 페이지 목록 자체가 원소가 되어 중첩 리스트가 됨 — extend와 다름
```

`page += 1`은 **현재 페이지를 성공적으로 처리한 뒤에만** 실행한다. 요청 전에 page를 올리면 첫 페이지를 빠뜨릴 수 있다.

### 6. 429와 잠시 기다리기

HTTP `429 Too Many Requests`는 일정 시간에 너무 많은 요청을 보냈다는 뜻이며, 서버와 다른 이용자를 보호하기 위한 호출 제한이다.

처리 순서: ① 현재 page 요청이 실패했다는 것을 기록 ② 응답의 `Retry-After` 또는 API 문서에서 대기 안내를 확인 ③ 안내된 시간만큼 기다림 ④ **page 번호를 올리지 않고 같은 page를 다시 요청**.

2페이지에서 429를 받았는데 3페이지로 넘어가면 2페이지 항목이 통째로 누락된다. **성공한 뒤에만 page를 올린다**는 원칙이 핵심이다.

이번 강의에서 다루지 않는 것: 지수 백오프 계산, 무작위 jitter, 여러 요청의 동시 실행, 분산 rate limiter — 8장의 안정성 주제로 남겨 둔다.

### 7. 빠뜨리거나 중복하는 실수 막기

1. **page를 0부터 시작** — API가 1부터 시작하는데 0을 보내면 오류나 빈 결과가 올 수 있다.
2. **실패했는데 page 증가** — 429나 500에서 page를 올리면 실패한 페이지가 누락된다.
3. **`page_size` 중간 변경** — 페이지 경계가 달라져 같은 항목을 다시 받거나 일부를 건너뛸 수 있다.
4. **`append`와 `extend` 혼동** — 전체 목록이 `[[...],[...]]`처럼 중첩될 수 있다.
5. **결과 건수를 확인하지 않음** — 수집 뒤 최소한 건수와 첫/마지막 ID를 출력하면 누락을 빠르게 발견할 수 있다.

### 8. 원본과 가공 파일을 나누는 이유 (3-2강)

API 응답에는 지금 쓰지 않는 필드도 포함될 수 있다. 수집 직후에는 '필요한 열만 남기면 깔끔해진다'고 생각하기 쉽지만, 파싱 실수를 나중에 발견하면 원본이 필요하다. **원본은 그대로 보존하고, 사용하기 쉬운 JSON/CSV를 별도로 만드는 2단 구조**를 사용한다.

| 파일 | 역할 |
| --- | --- |
| `raw_response.json` | API 응답 원본 보존 |
| `items.json` | 필요한 필드만 추출한 구조 |
| `items.csv` | 표 도구에서 쉽게 열 수 있는 구조 |
| `collection_log.json` | 출처와 수집 실행 정보 |

원본을 남기면 좋은 점: 필드 추출 실수를 다시 확인할 수 있고, 나중에 다른 필드가 필요해도 API를 다시 호출하지 않을 수 있으며, 제공자의 응답 구조가 바뀌었는지 비교할 수 있고, 정제 전 상태를 설명할 수 있다. **원본과 가공 결과에 같은 파일 이름을 사용하지 않는다.**

### 9. 필드 추출과 저장 옵션

```python
raw_items = raw_response.get("items")
if not isinstance(raw_items, list):
    raise ValueError("raw_response.items는 배열이어야 합니다.")
```

응답 구조가 예상과 다르면 빈 결과로 숨기지 않고 즉시 알린다. 새 딕셔너리를 만들어 추출하면 원본과 가공 결과가 섞이지 않는다.

| 옵션 | 이유 |
| --- | --- |
| `ensure_ascii=False` | 한글을 `\uXXXX`로 바꾸지 않음 |
| `indent=2` | 사람이 구조를 읽기 쉬움 |
| `sort_keys=True` | 객체 키 순서를 일정하게 저장 |
| `encoding="utf-8"` | 문자 인코딩을 명시 |

CSV는 `csv.DictWriter`에 `fieldnames`로 열 이름과 순서를 명시하고, 파일은 `newline=""` 옵션으로 연다. **문자열을 직접 `",".join(...)`으로 이어 붙이면 쉼표와 줄바꿈이 포함된 값을 잘못 처리할 수 있다** — 따옴표 처리는 `csv` 모듈에 맡긴다. 중첩 객체나 배열을 한 셀에 억지로 넣지 않고, 필요하면 별도로 펼치거나 JSON으로 남긴다.

실행 위치와 무관하게 같은 곳에 저장하려면 `Path("artifacts")` 같은 상대 경로 대신 `__file__` 기준 경로를 사용한다(노트북에서는 `Path.cwd()`로 분기).

### 10. 최소 수집 로그

| 필드 | 예시 |
| --- | --- |
| `collected_at` | `2026-07-16T09:00:00+09:00` |
| `source` | `fixture://news?page=all` |
| `item_count` | `5` |
| `status` | `success` |

**로그에 넣지 않을 것**: API 키 원문, `Authorization` header 전체, 개인정보가 포함된 전체 응답, 키가 query에 들어간 전체 URL.

`collected_at`은 우리가 받은 시각이며, 데이터 자체의 관측 시각이나 기준일은 `observed_at`, `data_date`처럼 별도 필드로 보존하고 두 값을 같은 것으로 가정하지 않는다.

### 11. 저장 결과 재현성

같은 입력과 같은 저장 규칙이면 파일 내용도 같아야 한다. 눈으로 확인할 것: 파일 이름이 같은가? JSON 구조와 건수가 같은가? CSV 열 순서가 같은가? 한글이 깨지지 않았는가? 로그에 키가 들어가지 않았는가?

`complete`와 `limited`의 구분도 중요하다 — 마지막 응답에 다음 페이지 신호가 없으면 `complete`(해당 조건의 페이지를 끝까지 받음), 다음 페이지가 있는데 최대 page에서 멈췄으면 `limited`(범위 제한에 따른 종료)다. 최대 범위에 도달했다고 종료 신호를 거짓으로 바꾸면 이 차이가 사라진다.

## Questions and Newly Learned Points

- 수집 중 일부만 실패했을 때 실제 데이터와 샘플을 섞으면 출처가 다른 자료가 하나의 결과가 된다 — 처음부터 다시 시작해 결과를 통째로 교체하는 편이 안전하다.
- 중복 글과 공백 제목을 수집 단계에서 지우면 받은 내용과 정제한 내용을 구분하기 어려워진다 — 이번 장은 수집과 저장을 다루므로 원본 상태를 그대로 남기고, 정제는 4장에서 다룬다.
- 줄바꿈이 있는 필드 때문에 CSV 파일의 눈에 보이는 줄 수는 글 수와 다를 수 있다 — CSV를 다시 읽었을 때 필드 내용이 유지되는지가 기준이다.
- 자주 하는 오해: "`page_size`는 클수록 항상 좋다"(서버 최댓값과 응답 크기·timeout 위험이 있다) / "빈 `items`면 언제나 마지막이다"(필터 조건이나 일시적 결과일 수 있다) / "429는 API 키가 틀렸다는 뜻이다"(인증 실패는 주로 401) / "반복 수집은 동시에 많이 보내야 빠르다"(입문 단계에서는 순차 수집이 흐름을 이해하고 호출 한도를 지키기 쉽다) / "JSON이면 언제나 표로 바로 바꿀 수 있다"(중첩 객체와 배열이 있으면 어떤 행과 열로 펼칠지 먼저 정해야 한다).
