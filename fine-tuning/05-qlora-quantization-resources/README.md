## 학습 목표
- 양자화가 값 대신 **대표값의 번호 + scale**을 저장하는 것임을 작은 예제로 설명한다.
- n비트 = 대표값 2ⁿ개, 균등 코드북과 NF4(0 근처 촘촘)의 차이를 설명한다.
- 블록 크기 64 · FP32 scale · 이중 양자화(256개씩)로 가중치당 비트 4.5 → 4.127을 계산한다.
- "4비트 모델"이어도 **저장(NF4) · 계산(BF16/FP32) · 비양자화 층과 어댑터(FP32)**가 다르다는 걸 구분한다.
- `BitsAndBytesConfig`의 인자를 저장용 · 계산용으로 나누고, prepare → LoRA 순서가 왜 중요한지 설명한다.
- 양자화(가중치 저장)와 LoRA(기울기 · 옵티마이저 상태)가 **줄이는 곳이 다르다**는 걸 설명한다.
- 품질 · 메모리 · 시간을 같은 구간에서 재고 따로 읽는다. 0.5B에서 이득이 안 보이는 이유를 설명한다.
- 같은 revision + 같은 양자화 + 같은 prepare로 어댑터를 복원해 logits · 원문을 확인한다.

## 핵심 이론

### 5-1. 양자화와 계산 정밀도 구분하기

#### ① 양자화 = 가까운 대표값의 "번호"로 저장

숫자를 몇 개 안 되는 **대표값(codebook)** 중 가장 가까운 것으로 반올림하고, 값 대신 **그 대표값의 번호**를 저장해요.

```python
weights  = torch.tensor([-2.0, -0.9, 0.2, 1.3, 2.0])
scale    = weights.abs().max()                         # 2.0  (블록의 최대 절댓값)
codebook = torch.tensor([-1.0, -1.0 / 3, 1.0 / 3, 1.0]) # 2비트 = 대표값 4개 (균등)

indices = (weights[:, None] / scale - codebook[None, :]).abs().argmin(dim=1)
restored = scale * codebook[indices]
```

| 원래 값 | ÷ scale 2.0 | 가장 가까운 대표값 | 저장하는 번호 | 복원값 (scale × 대표값) |
|---|---|---|---|---|
| −2.0 | −1.0 | −1.0 | 0 | −2.0 |
| −0.9 | −0.45 | −1/3 | 1 | −0.6667 |
| 0.2 | 0.1 | 1/3 | 2 | 0.6667 |
| 1.3 | 0.65 | 1/3 | 2 | 0.6667 |
| 2.0 | 1.0 | 1.0 | 3 | 2.0 |

- 순서: ① scale로 나눠 −1\~1로 맞추기 → ② 가장 가까운 대표값 찾기 → ③ **번호 + scale만 저장** → ④ 쓸 때 `scale × codebook[번호]`
- 0.2와 1.3이 둘 다 0.6667이 돼요. 최대 오차 **0.6333**. 압축은 공짜가 아니에요.
- **메모리가 줄어드는 건 ③ 저장할 때**예요. ④ 곱하기는 쓸 때 근삿값으로 되돌리는 단계예요.

**`[:, None]`과 브로드캐스팅**

```text
weights[:, None] / scale   (5, 1)   ← 세로로 세움 (unsqueeze(1)과 같음)
codebook[None, :]          (1, 4)   ← 가로로 눕힘
뺄셈 → (5, 4) 거리 표: 가중치 5개 × 대표값 4개
.abs().argmin(dim=1) → 행마다(가중치마다) 가장 가까운 열 번호 → (5,)
```

#### ② 2비트 vs 4비트, 균등 vs NF4

- n비트면 번호가 2ⁿ개 → 2비트 4칸, **4비트 16칸**. 비트가 많을수록 오차는 줄고 메모리는 늘어요.
- **NF4**(4-bit NormalFloat): 가중치는 대체로 0 근처에 몰린 종 모양이라, 16칸을 **0 근처에 촘촘하게**(간격 약 0.08\~0.09), 양끝은 듬성하게(약 0.28\~0.30) 둬요.

```text
NF4 코드북 (셀에서 찍은 첫 4비트 층 quant_state.code)
[-1.0, -0.6962, -0.5251, -0.3949, -0.2844, -0.1848, -0.0911, 0.0,
  0.0796, 0.1609, 0.2461, 0.3379, 0.4407, 0.5626, 0.723, 1.0]
```

같은 예제를 4비트로 바꿔 보면 (내가 질문해서 계산해 본 것):

| 코드북 | 번호 | 최대 오차 |
|---|---|---|
| 2비트 균등 (원래 예제) | [0, 1, 2, 2, 3] | 0.633 |
| 4비트 균등 `torch.linspace(-1, 1, 16)` | [0, 4, 8, 12, 15] | **0.1** |
| NF4 (위 16개) | [0, 3, 8, 14, 15] | 0.146 |

- 이 예제에선 NF4가 균등보다 오차가 커요. 값들(−0.45, 0.65)이 0 근처가 아니라 **바깥쪽**에 있어서예요. NF4는 실제 가중치처럼 0 근처에 많이 몰린 분포에서 유리해요.
- 코드북을 16칸으로 바꾸면 노트북의 assert도 `indices.max() < 16`으로 같이 바꿔야 해요.

#### ③ scale 비용과 이중 양자화: 4.5 → 4.127비트

```python
weight_bits = 4
single_scale_bits = 32 / 64                      # 0.5   → 합계 4.5 bits/weight
nested_scale_bits = 8 / 64 + 32 / (64 * 256)     # 0.127 → 합계 4.126953 bits/weight
```

| 숫자 | 뜻 |
|---|---|
| **64** | 가중치 64개를 한 블록으로 묶어 scale 1개를 같이 씀 (튀는 값 하나가 전체 scale을 망치지 않게 작게 나누되, scale이 너무 많아지지 않는 타협) |
| **32** | scale 하나를 FP32로 저장하는 크기. 블록마다 다른 보통 소수고, 64개 가중치에 다 곱해지니 정확해야 함 |
| **8** | 이중 양자화로 scale도 8비트로 줄임 |
| **256** | scale 256개를 다시 묶어 FP32 기준값 1개를 같이 씀 → 기준값 하나가 64 × 256 = 16,384개 가중치를 담당 |

- scale을 FP32로 두면 가중치 하나당 32/64 = **0.5비트**가 더 붙어 4.5비트.
- **double quantization** = scale을 8비트로 다시 양자화 + 256개마다 FP32 기준값 1개 → 8/64 + 32/16,384 = 0.127비트 → 합계 **4.127비트**, 가중치당 **0.373비트** 절약.
- 다시 줄이는 대상은 **가중치가 아니라 scale**이에요. 가중치를 두 번 양자화해서 2비트로 만드는 게 아니에요.
- 계산할 때는 거꾸로 풀어요: **기준값으로 scale 복원 → scale로 가중치 복원 → BF16 행렬곱 → 다 쓰면 버림.**
- 경계 블록 · 코드북 등을 뺀 설명용 계산이라 실제 파일 크기와는 달라요.

| 저장하는 것 | 크기 | 몇 개마다 하나 |
|---|---|---|
| 가중치 번호 | 4비트 (NF4) | 1개마다 |
| scale | 8비트 | 가중치 64개마다 |
| 기준값 | 32비트 (FP32) | scale 256개마다 |

#### ④ 저장 · 계산 · 안 압축된 층은 따로

| 구분 | dtype (셀 14 출력) | 뜻 |
|---|---|---|
| ① 저장 `packed_weight` | `torch.uint8` | 8비트 양자화가 아니라 **1바이트에 4비트 번호 2개를 담은 상자** |
| ② 계산 `linear_compute` | `torch.bfloat16` (T4: FP32) | 4비트끼리 곱하지 않음. 근삿값으로 풀어서 곱함 |
| ③ 임베딩 (prepare 전 → 후) | bf16 → **float32** | 비양자화 층을 prepare가 FP32로 키움 |
| ③ 어댑터 A · B | `torch.float32` | 학습하는 부분 |

- bitsandbytes는 **Linear 층(q · k · v · o · gate · up · down)만** 4비트로 바꿔요. 임베딩 · Norm · bias는 압축되지 않아요.
- 그래서 "QLoRA = 메모리 1/4"이 성립하지 않아요. 1/4은 **양자화된 선형층의 가중치 저장**에만 해당해요.

#### ⑤ 양자화와 LoRA는 줄이는 곳이 달라요 (BF16 기준 계산값)

| 방법 | 모델 가중치 | 기울기 + AdamW 상태 | 줄인 것 |
|---|---|---|---|
| 3장 전체 SFT | 0.92 GiB | 2.76 GiB | – |
| 4장 LoRA (q · v) | 0.92 GiB | 0.006 GiB | 학습 대상 → 기울기 · 상태 |
| 5장 QLoRA (q · v) | 0.68 GiB | 0.006 GiB | + 기반 가중치 저장 |

- **양자화는 가만히 있는 큰 가중치를 작게 저장**하고, **LoRA는 움직이는 파라미터를 적게** 해요. 서로 대신할 수 없어요.
- AdamW는 학습 파라미터마다 기울기 1 + 상태 2 = 세 벌을 더 들고 있어요.

### 5-2. NF4 기반 모델에 LoRA 학습하기

구조는 4장 그림에서 **W만 Ŵ(근사 가중치)**로 바뀌어요: h = Ŵx + (α/r)·BAx, α/r = 16/8 = 2.
기울기는 Ŵ 계산을 **지나가지만 Ŵ를 고치지는 않아요.** optimizer는 A · B만 갱신해요.

```python
quantization_config = BitsAndBytesConfig(
    load_in_4bit=True,                      # 4비트 층으로 로드
    bnb_4bit_quant_type="nf4",              # 저장: NF4
    bnb_4bit_use_double_quant=True,         # 저장: scale까지 압축
    bnb_4bit_compute_dtype=COMPUTE_DTYPE,   # 계산: BF16 / FP32
    bnb_4bit_quant_storage=torch.uint8,     # 저장 상자
)
# from_pretrained(..., quantization_config=..., device_map={"": 0}, dtype=COMPUTE_DTYPE)
#   dtype = 양자화 "안 되는" 층의 자료형, device_map {"": 0} = GPU 0번에 통째로
```

- `BitsAndBytesConfig`는 모델이 아니라 "이렇게 읽어 달라"는 **주문서**예요. 값 하나만 바꿔도 Ŵ가 달라지니 통째로 기록해요.
- **prepare → LoRA 순서**: `prepare_model_for_kbit_training`이 ① 전부 얼리고 ② 비양자화 층을 FP32로 키우고 ③ gradient checkpointing을 켜요. 그다음 `get_peft_model`. **순서가 반대면 새로 붙인 A · B까지 얼어요.**
- 붙인 뒤 검사: 학습 대상 540,672개 · 이름이 전부 `lora_` · 기반 층이 `Linear4bit`.

**`get_memory_footprint` 구성 (슬라이드 계산)**

| | 파라미터 수 | 로드 직후 | prepare 뒤 |
|---|---|---|---|
| NF4 선형층 번호 (scale 제외) | 357,826,560 | 178.9 MB | 178.9 MB |
| 임베딩 (출력층과 공유) | 136,134,656 | 272.3 MB | **544.5 MB** |
| Norm · bias | 71,552 | 0.14 MB | 0.29 MB |
| LoRA A · B | 540,672 | – | 2.16 MB |
| 합계 | 494,573,440 | **451.3 MB** | **725.9 MB** |

- 늘어난 275 MB 중 **272 MB가 임베딩 BF16 → FP32**. prepare 뒤 모델의 **약 75%가 FP32 임베딩**이에요.
- 슬라이드 원본 결과(lr 2e-5): dev loss **1.0459 → 0.9745** · 25.3초. B ≠ 0 · 기반 가중치 그대로. 그런데 답에 status가 없고 인용 ID를 "政策01-v1"로 번역해 버림 → **손실이 내려갔다고 답이 맞게 된 건 아니에요.**

### 5-3. 품질, 메모리와 시간을 함께 비교하기

| (슬라이드 · RTX 5060 BF16) | dev loss | 학습 최대 메모리 | 학습 시간 | 형식 (dev 12) |
|---|---|---|---|---|
| 4장 LoRA | 0.9207 → 0.8717 | 1.615 GiB | 18.5초 | 0/12 (코드 펜스 10 · "answered" 한 단어 2) |

### 5-4. 새 세션에서 모델 복원하기

- ZIP에 들어가는 것: `qlora_report.json`(설정 · 원문 · 기준 logits 151,936개라 약 3.9 MB) + `adapter_config.json` + `adapter_model.safetensors`(2,175,168바이트 ≈ 2.1 MiB, FP32).
- ZIP에 **없는 것**: 기반 모델 가중치 · optimizer · scheduler · 병합 모델. 복원은 **추론을 다시 만드는 것**이지 학습 재개가 아니에요.
- 복원 순서는 학습 때와 똑같이: ① 같은 revision NF4 로드 → ② **같은 prepare**(재계산만 끔) → ③ `PeftModel.from_pretrained(..., is_trainable=False)` → ④ logits `allclose(atol=1e-4, rtol=1e-4)` + 생성 원문 일치.
- prepare를 빠뜨리면 FP32로 키운 비양자화 층이 달라서 결과가 달라요. **BF16으로 만든 ZIP은 T4에서 복원을 거부**해요.
- 보고서 config는 실제 학습 인자가 아니라 `expected_config`를 풀어 기록해요 → 설정을 바꾸면 여기도 같이 고쳐야 해요(4장에서 내가 놓친 부분과 같은 함정).
- 슬라이드 원본은 그 PC에서 복원 검사를 통과하지 못했고, 그대로 기록했어요. 설정 바꿔 보기(lr 2e-4 · all-linear · atol 1e-4)는 BF16 실측에서 통과.

## 질문과 새로 알게 된 점

### 양자화 코드에서 무엇을 저장하나 (내 이해 확인)
> 내가 이해한 흐름: 가중치를 scale(`abs().max()`)로 나누고, 코드북과 뺀 값이 가장 작은 index = 가중치/scale이 가장 가까운 대표값. 메모리를 줄이려고 그 index와 scale을 곱해서 근삿값을 계산한다?

- 흐름은 맞아요. 다만 **메모리가 줄어드는 건 index + scale만 저장할 때**예요. 곱하기는 쓸 때 되돌리는 단계라 메모리를 줄이는 게 아니에요.
- "정규분포를 나타내는 codebook(0 근처에 몰린 형태)"은 **NF4** 이야기예요. 수업 예제는 균등 간격 2비트예요.

### `[:, None]`은 뭐지?
- 크기 1짜리 축을 끼워 넣어서 (5,) → (5, 1)로 세로로 세우는 것. `unsqueeze(1)`과 같아요.
- (5, 1) − (1, 4)는 브로드캐스팅으로 (5, 4) 표가 돼서, 가중치마다 모든 대표값과의 거리를 한 번에 계산해요.

### 2비트와 4비트 차이는?
- 번호에 쓰는 비트 수. 2비트 = 2² = 4칸, 4비트 = 2⁴ = 16칸. 칸이 많을수록 가까운 대표값이 생겨 오차가 줄고, 대신 번호 하나가 커져요. QLoRA는 그 균형으로 4비트를 써요.

### 왜 scale이 32비트야? 왜 64개가 나눠 쓰지?
- 32는 "scale 숫자 하나의 크기"(FP32). 64는 "몇 개가 scale 하나를 같이 쓰나"라는 **묶는 규칙**이에요. 둘은 다른 종류의 숫자예요.
- 64개마다 1개면 가중치 하나당 32/64 = 0.5비트. 블록을 더 키우면 scale 비용은 줄지만 튀는 값 하나에 블록 전체 정밀도가 망가지고, 더 작게 나누면 scale이 너무 많아져요.

### scale이 FP32라 32비트였는데 갑자기 256 × 64는 뭐야?
- 256은 **scale을 다시 묶는 규칙**이에요. scale도 8비트로 줄이고, scale 256개마다 FP32 기준값 1개를 둬요.
- 기준값 하나가 scale 256개를 담당하고, scale 하나가 가중치 64개를 담당하니까, 기준값 하나가 가중치 256 × 64 = 16,384개를 담당해요. 그래서 가중치 하나당 기준값 비용은 32 / 16,384 ≈ 0.002비트로 거의 공짜예요.

### scale도 나중에 계산할 때 복원해? 그럼 가중치는 4비트, scale은 8비트?
- 네. 계산할 때 **기준값으로 scale부터 복원 → 그 scale로 가중치 복원 → BF16 곱셈**이에요.
- 정리하면 가중치 번호는 4비트(NF4), scale은 8비트, scale을 되돌리는 기준값만 32비트(FP32).

### 임베딩을 왜 FP32로 바꾸나? 양자화 때문에 loss가 너무 오를까 봐? (사이드 질문)
- **반만 맞음.** 양자화 오차를 메우려는 게 아니라, **압축하지 않은 층을 학습 중에 안정적으로 계산하려는** 거예요.
- 임베딩은 NF4로 압축되지 않아요(Linear 층만 4비트). prepare가 BF16 → FP32로 키우는 이유는 **수치 안정성**:
  - BF16은 유효 숫자가 적어서 작은 기울기나 차이가 반올림으로 사라질 수 있어요.
  - Norm · softmax · logits(어휘 약 15만 개)는 정밀도에 예민하고 손실로 바로 이어져요.
  - 임베딩은 출력층(lm\_head)과 가중치를 공유해요.
- 대가는 메모리: 451 MB → 726 MB, 늘어난 양 중 272 MB가 임베딩. LoRA A · B도 같은 이유로 FP32 → 어댑터 540,672 × 4바이트 ≈ 2.1 MB.

> 한 줄: 4비트로 얼린 몸통 위에서 학습할 때 **기울기와 loss 계산이 흔들리지 않게** 압축 안 된 층을 FP32로 둔다.

## 추가 실습 `5장_추가_Unsloth.ipynb`

### 1부. 모델 크기를 키우며 SFT · LoRA · QLoRA 비교

| 방법 | 학습 대상 | 기반 모델 | lr |
|---|---|---|---|
| SFT | 전체 | BF16 | 2e-5 |
| LoRA | A · B | BF16 고정 | 2e-4 |
| QLoRA | A · B | NF4 + prepare | 2e-4 |
| QLoRA-noprep | A · B | NF4, prepare 없음 | 2e-4 |

노트북 참고 실측(L4, 1회, 학습 최대 메모리):

| 모델 | SFT | LoRA | QLoRA | QLoRA-noprep |
|---|---|---|---|---|
| 0.5B | 4.65 GiB | 1.66 GiB | 1.69 GiB (+2%) | 1.17 GiB (−30%) |
| 4B | OOM | 8.47 GiB | 4.99 GiB (−41%) | 3.47 GiB (−59%) |
| 14B | OOM (로드) | OOM (로드) | 15.08 GiB | 10.58 GiB |

- **SFT가 먼저 탈락.** 가중치 + 기울기 + AdamW m · v로 가중치의 약 4배가 필요해요.
- **그다음 LoRA가 탈락.** 기반 모델이 BF16 그대로라 14B는 올리는 것만으로 27.5 GiB.
- **QLoRA는 기반 모델까지 줄여요.** 모델이 클수록 효과가 커지고, 14B는 QLoRA로만 학습할 수 있어요.
- **0.5B에서 이득이 없는 이유**
  - 선형층에서 아끼는 양: 파라미터당 1.48바이트
  - 단어표에서 늘어나는 양: 파라미터당 4바이트 (FP32로 +2, BF16 사본 +2)
  - 본전이 되는 단어표 비중: 1.48 ÷ 5.48 ≈ **27%** → 0.5B는 27.6%로 본전, 4B는 9.7%라 이득이 남아요.
- noprep으로 prepare를 빼면 메모리는 더 줄지만, NaN과 품질을 확인한 뒤에만 빼요.
- 고르는 순서: **LoRA가 들어가면 LoRA, 안 들어가거나 빠듯하면 QLoRA.** 4B는 LoRA도 12/12라 L4에선 LoRA가 합리적. 모델은 **목표를 넘는 가장 작은 것**.

### 2부. Unsloth
- **새 학습 방법이 아니라 LoRA · QLoRA를 빠르게 돌리는 최적화 도구**예요.

  | 하는 일 | 1부 (직접) | Unsloth |
  |---|---|---|
  | 4비트 로딩 | `BitsAndBytesConfig` | `load_in_4bit=True` |
  | 준비 + LoRA | prepare + `get_peft_model` | `FastLanguageModel.get_peft_model` |
  | 학습 | 반복문 · optimizer · scheduler | TRL `SFTTrainer` |
  | 내보내기 | 별도 도구 | `save_pretrained_gguf` |

- 흐름: 불러오기 → 학습 전 답 → LoRA 붙이기(`for_training`) → `SFTTrainer` → `for_inference` 뒤 학습 후 답 → 어댑터 저장 · 복원.
- `prompt` / `completion`으로 넣으면 토큰화와 `-100` 마스킹을 **자동으로** 해줘요(3장에서 손으로 한 것).
- `unsloth`는 transformers · trl보다 **먼저 import**. 설치 뒤 세션 재시작.
- "2배 빠르고 메모리 70% 절감"은 개발사 수치라 직접 다시 재봐야 해요.
- **쓰기 좋은 경우**: 빠른 PoC, 반복 실험, GPU가 제한된 사내 환경, GGUF 로컬 배포.
- **피하는 경우**: 프롬프트나 RAG로 충분할 때, 지원 안 하는 모델, 학습 루프를 깊게 고쳐야 할 때, 대규모 서빙(vLLM).

> 핵심: **LoRA냐 QLoRA냐는 "GPU에 들어가느냐"로, Unsloth를 쓰느냐는 "빨리 반복해야 하고 지원되는 모델이냐"로** 정한다.
