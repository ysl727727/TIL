## 2. 전체 구조

```
입력: 두 사람의 성별 · 생년월일 · 생시(모름 가능) · MBTI
   ↓
만세력 계산 (1번만): 8글자 → 오행 · 강약 · 온도 · 필요한 기운 → 두 사람 관계(합·충·원진)
   ├─ 단어형 텍스트 v5 → klue/bert (4축 각각 0.5 기준) → 16유형 (예: T13)
   └─ 서술형 텍스트 v2 ─┐
                       ↓
        LangChain: Prompt | Model(GPT-6 Luna) | Parser(JSON 6칸)
                       ↓
        규칙 점검 → 위반이면 1회 재작성 → 최종 검증 → 결과 화면
```

- **4축**: 연애 케미(닮은꼴/보완형) · 연애 온도(열정형/안정형) · 관계 거리(밀착형/독립형) · 갈등 해결(바로 풀기/시간 두기). 두 극은 우열이 없다.
- **판단은 BERT, 설명은 LLM.** 고르는 일(분류)과 쓰는 일(생성)을 나눴다.

## 3. 분류 모델: 0.079 → 0.831

### 3-1. 한 장 요약

| 단계 | 한 일 | 결과 (macro-F1) | 배운 점 |
|---|---|---|---|
| 1 | AI가 검수한 라벨 600쌍으로 TF-IDF·BERT 학습 | test **0.079** | 16유형 찍기(약 0.06)와 비슷 |
| 2 | 원인 분석 | 숫자 특징 0.264 vs 문장 텍스트 0.10 | 텍스트가 판단 정보를 흐림 |
| 3 | 정보를 다 넣은 고정 형식 텍스트 | 0.11~0.13 | 텍스트만 고쳐선 부족 → 라벨이 흔들림 |
| 4 | GPT-6 Luna에게 규칙 없이 직접 분류 | 0.101 | LLM도 못 맞힘 → 정답은 "느낌"이 아니라 규칙의 계산 결과여야 함 |
| 5 | **판단 기준(v1.2)을 코드로 구현** (`labeler.py`) | AI 검수 라벨과 16유형 82% 일치 | 같은 입력이면 항상 같은 정답 |
| 6 | 텍스트에서 빠진 판단 정보 2개 보충 | 같은 텍스트·다른 라벨 0건 | 판단 재료가 **빠짐없이** 있어야 함 |
| 7 | 데이터 360 → 1,200 → 2,400 → 4,800쌍 | 0.165 → 0.532 → 0.726 → 0.757 | 데이터 양 효과가 큼 |
| 8 | 2,400쌍에서 학습률 5e-5 | **0.041 (학습 붕괴)** → 2e-5로 0.726 | 학습률이 크면 통째로 무너짐 |
| 9 | RoBERTa | 0.450 → 설정 조정 후 0.777 | 모델마다 설정을 따로 맞춰야 함. 결국 BERT와 비슷 |
| 10 | **dev 1,200쌍 신설** | validation 1위가 dev에선 3위 | 120쌍으론 0.76과 0.78을 구분 못 함 |
| 11 | **축별 분류** (출력 4개) | dev 0.714 → 0.744 | 라벨이 축별 규칙이니 모델도 축별로 |
| 12 | 텍스트 보강 (삼합 위치, MBTI 글자별 비교) | 0.734 (효과 없음) | BERT가 이미 스스로 비교하고 있었음 |
| 13 | **어려운 사례 1,200쌍 추가** | dev **0.802** | 가장 큰 효과. 경계 사례를 직접 보여 줘야 함 |
| 14 | 규제 (A/B 바꾸기, dropout, weight decay, label smoothing) | dev 0.793 (같은 수준) | 과적합은 줄었지만 정확도는 그대로 → 남은 오차는 과적합 때문이 아님 |
| 15 | 동률 사례 1,200쌍 추가 | dev 0.795 | 드문 경로라 전체 영향 작음 |
| 16 | validation으로 선정 → **test 1회** | **0.831 / 0.858 (103/120)** | test는 이 한 번만 사용 |

### 3-2. 가장 중요했던 고민: "모델이 문제인가, 정답이 문제인가"

- 0.079가 나왔을 때 처음엔 모델을 바꾸려 했다. 하지만 원인을 파 보니 **정답(라벨)이 흔들리고 있었다.**
  - AI 라벨은 비슷한 입력에도 답이 달랐다.
  - LLM에게 직접 맞히게 해도 0.101이었다. 사람이 봐도 "왜 이 유형인지" 일관된 기준이 없었다는 뜻이다.
- 해결: 팀의 판단 기준 문서(v1.2)를 **코드로 옮긴 규칙 라벨러**를 만들었다.
  - 축마다 두 극에 사주 점수를 더한다 (강한 신호 2 · 보통 1 · 약한 0.5).
  - 차이가 **1.5 이상**이면 사주로, 작으면 **MBTI**로, 그래도 같으면 근소 우위 → 마지막 규칙.
  - 4축 결과를 합쳐 16유형 (`T = 1 + 8c + 4t + 2d + g`).
- 효과: 데이터를 늘릴수록 점수가 올라가기 시작했다. **배울 수 있는 정답이 생긴 것.**

### 3-3. TF-IDF vs BERT: "조각을 세는 것"과 "읽는 것"

| | TF-IDF + 로지스틱 회귀 | klue/bert-base 축별 |
|---|---|---|
| 읽는 법 | 2~4글자 조각이 몇 번 나오는지 셈 | 문장 전체를 순서·관계까지 읽음 |
| validation macro-F1 | 0.428 | **0.767** |
| 갈등 축 정확도 (dev) | 0.766 | **0.946** |

- 실제 오답 예: 정답 규칙은 "충과 원진의 중요도가 같으면 태그로 비교 → 충이 더 무거움 → 바로 풀기"였다.
- TF-IDF는 "필요막음" 조각이 4번 나온 것만 보고 시간 두기로 틀렸다. **조건 비교는 조각 개수로 흉내 낼 수 없다.**

### 3-4. LLM에게 규칙만 설명하면? (곱의 함정)

- 상용 LLM(Jev)에게 규칙을 설명하고 축마다 고르게 했더니, 한 축 정확도는 약 0.8이었다.
- 하지만 유형은 **네 축이 모두 맞아야** 정답이다: 0.8⁴ ≈ 0.41, 실제 0.43.
- BERT는 정답 예시 12,000행으로 학습해서 축마다 약 0.95: 0.95⁴ ≈ 0.81.
- 교훈: **설명을 듣는 것과 예시로 배우는 것은 다르다.** 축 정확도를 조금만 올려도 최종 점수가 크게 오른다.

### 3-5. 하이퍼파라미터: 무엇을 왜 바꿨나

| 항목 | 변화 | 이유 | 결과 |
|---|---|---|---|
| batch | 8 고정 | 다른 조건만 바꿔 비교 | - |
| learning rate | 5e-5 → **2e-5** | 2,400쌍에서 학습 붕괴 (손실이 찍기 수준 2.7에서 멈춤) | 같은 데이터 0.041 → 0.726 |
| epoch | 20 → 30 시도 → **15** | 30이 20보다 나아지지 않음 (0.512 vs 0.532), 4,800쌍부터 11~15에서 최고점 | 15 중 dev 기준 14번째 선택 |
| 규제 | dropout 0.1→0.2, weight decay 0.01→0.05, label smoothing 0→0.1, A/B 자리 바꾸기 | 학습 손실 0.01 = 외우는 징후 | 손실 0.22, dev 0.802 → 0.793 (유지) |
| class weight | balanced (처음부터) | 주 지표 macro-F1은 드문 유형도 1/16 비중 | 별도 비교 안 함 |

- **설정은 점수를 지키는 역할, 점수를 올린 건 정답과 데이터였다.**

### 3-6. 평가 설계: 세트를 왜 넷으로 나눴나

| 세트 | 크기 | 역할 |
|---|---|---|
| train | 6,000쌍 (A/B 바꾸기로 12,000행) | 학습 |
| dev | 1,200쌍 | 실험 비교 + epoch 선택 |
| validation | 120쌍 | 최종 후보 선정 |
| test | 120쌍 | 마지막 **1회** 확인 |

- 한 사람이 여러 커플에 나오므로 **사람 단위로 묶어 분할**해서 누수를 막았다.
- 데이터는 시드 고정으로 생성하고, 블록을 뒤에 덧붙여도 앞 데이터가 바뀌지 않게 했다(재현 가능).

## 4. 만세력 계산: 숫자 이전에 "입력이 맞는가"

- 사용한 만세력 라이브러리(lunar-python)는 중국 기준이라 그대로 쓰면 두 가지가 어긋난다.

| 문제 | 해결 |
|---|---|
| 절기 시각이 중국 시간(UTC+8) → 한국과 1시간 차이, 입춘 전후 출생자의 년주·월주가 바뀔 수 있음 | 년주·월주 판정 때만 한국 시각을 중국 시간으로 바꿔 비교 |
| 한국의 과거 시간 제도: 서머타임(1948~51, 1955~60, 1987~88), 30분 늦은 표준시(UTC+8:30, 1954~61) | 입력을 "당시 시계 시각"으로 보고 `Asia/Seoul` 시간대로 현재 한국 표준시 환산 |

- 예: 1988년 서머타임 중 "아침 9시" → 표준시 8시(진시). 보정 없으면 사시로 틀림.
- 기존 방식에서는 944명 중 16명의 시주가 틀렸다.
- 검증: 공개 입춘 시각 4/4, 경계 사례 20/20, 무작위 3,000명 독립 구현 대조 100% 일치.
- 오픈소스 만세력(manseryeok) README 예시와 같은 입력을 넣었을 때도 결과가 일치했다.

## 5. LangChain 해설

### 5-1. 체인 구조

```
draft  = prompt() | model | JsonOutputParser
repair = repair_prompt() | model | JsonOutputParser
explain_chain = 초안 → 규칙 점검(checks.py) → (위반이면) 1회 재작성 → 최종 검증(_finalize)
```

- **Prompt**: 작성 규칙 + BERT가 정한 유형(이 커플의 극만) + 서술형 사주 텍스트
- **Model**: GPT-6 Luna ↔ Ollama 로컬 모델을 같은 자리에 교체
- **Parser**: 요약 1 · 강점 2 · 맞춰 갈 점 2 · 대화 팁 1의 JSON 6칸으로 강제
- LangChain을 쓴 이유: **모델 자리만 바꿔 같은 조건으로 비교**할 수 있고, 점검·재작성 흐름을 체인으로 이을 수 있다.

### 5-2. 하나의 계산, 두 개의 텍스트

| | 단어형 v5 → BERT | 서술형 v2 → LLM |
|---|---|---|
| 목적 | 판단 재료 전부 | 해설에 쓸 문장 근거 |
| 숫자 | 그대로 (신강 0.56) | 말로 (기운이 강한 편) |
| 관계 | 전부 | 최대 7개 |
| MBTI | 코드 그대로 | 풀어 씀 (ENFP → 외향·직관·감정·인식) |

- 같은 사주 계산에서 두 텍스트를 만들어, BERT와 LLM이 서로 다른 사주를 보는 일을 막았다.
- MBTI 코드를 풀어서 넘긴 이유: 출력에서 MBTI 코드가 금지인데, 입력에 있으면 그대로 베낀다.

### 5-3. 모델 선택 기준

- 비교 전에 기준을 먼저 고정했다: 같은 24건, 같은 프롬프트, 로컬은 temperature 0.3 · seed 42.
- 채점: 24건 중 **규칙 위반이 하나라도 있는 건수**
  - 형식(JSON 6칸)·길이, MBTI 코드·한자·Markdown 노출, 입력에 없는 관계 지어내기, 반대 극 언급, 단정("반드시", "운명"), 우열("더 좋은 유형")
- 우선순위: **품질 > 비용 > 시간 > 개인정보**
  - 처음엔 개인정보를 1순위로 뒀다가 바꿨다. 해설은 사용자에게 그대로 보이니 품질이 먼저이고, 외부 전송은 동의를 받고 서버에 저장하지 않는 것으로 관리할 수 있다고 판단했다.
- 자동 채점은 거름망. 순위가 비슷하면 결과를 직접 읽었고, 그렇게 자동 채점이 놓친 Markdown 노출을 찾았다.

| 모델 (최종 24건) | 위반 | 시간 | 비용 |
|---|---|---|---|
| **GPT-6 Luna** (클라우드) | 3 → 0 | 7.0초 | 약 1센트 |
| qwen2.5:7b (로컬) | 4 | 6.3초 | 0 |
| qwen3:4b (로컬) | 6 | 5.2초 | 0 |
| gemma3:12b (로컬) | 6 | 32.4초 | 0 |
| gemma4:e4b (로컬) | 10 | 3.2초 | 0 |

- Luna 선택: 품질 1위 + 서버가 Vercel(CPU)이라 로컬 모델을 올릴 수 없음. 모델 자리만 바꾸면 qwen2.5:7b로 교체 가능.

### 5-4. 증상과 원인: 3/24 → 0/24 → 0/24

| 단계 | 결과 | 의미 |
|---|---|---|
| v2 첫 초안 | 3/24 반대 극 언급 | 열정형 커플 해설에 "안정형" 비교 문장 |
| + 점검 후 재작성 | 0/24 | 증상은 해결, 대신 시간·비용 증가 |
| v4 프롬프트 | 첫 초안부터 0/24, 재작성 0, 비용 −21% | 원인 해결 |

- 원인: 프롬프트가 **두 극을 모두 설명**하고 있었다. → 이 커플의 극만 보여 주고, 반대 극 이름 금지를 처음부터 명시.
- 그래도 형식·금지 표현이 남으면 결과를 내보내지 않고 다시 시도 안내만 한다.

### 5-5. 분류와 해설을 한 체인으로 묶지 않은 이유

- BERT는 CPU에서 금방 끝나고, 해설은 응답을 기다리느라 5~10초 걸린다.
- 한 체인으로 묶으면 해설이 끝날 때까지 BERT 자리를 붙잡아 다른 요청이 기다린다.
- 그래서 서비스는 두 단계를 따로 부르고, 동시 처리 한도도 따로 둔다. 묶은 `analysis_chain`은 테스트에서만 쓴다.

## 6. 오늘의 교훈 (TIL)

1. **모델보다 정답이 먼저다.** 정답이 흔들리면 어떤 모델도 배울 수 없다. 0.079 → 0.71의 대부분은 라벨을 규칙으로 고정한 효과였다.
2. **입력에 판단 재료가 빠짐없이 있어야 한다.** "같은 텍스트인데 정답이 다른 경우"를 세 보면 누락을 찾을 수 있다.
3. **평가 세트가 작으면 순위를 믿을 수 없다.** 120쌍 validation 1위가 1,200쌍 dev에서는 3위였다.
4. **쉬운 예시를 더 주기보다 헷갈리는 예시를 주는 게 효과가 크다.** (오답 노트)
5. **과적합을 줄였는데 점수가 그대로면, 남은 오차는 과적합이 아니다.** 원인을 다시 봐야 한다.
6. **학습률은 작은 차이로 학습 전체를 무너뜨릴 수 있다.** (5e-5 → 0.041)
7. **여러 단계를 모두 맞혀야 하는 문제는 곱으로 계산된다.** 0.8⁴ = 0.41, 0.95⁴ = 0.81.
8. **증상을 막는 장치(재작성)와 원인을 고치는 것(프롬프트)은 다르다.** 둘 다 필요하지만 원인을 고쳐야 비용이 준다.
9. **자동 채점은 거름망이다.** 마지막엔 사람이 결과를 읽어야 한다.
10. **기준은 비교 전에 정한다.** 결과를 보고 기준을 바꾸면 비교가 의미 없어진다.

## 8. 개선 방향

- **실제 검증**: 사용자 피드백("맞았다/아니다")으로 규칙과 유형이 체감과 맞는지 확인
- **라벨 신뢰도**: 두 사람 독립 라벨링 + 일치도(kappa) 측정, 명리 전문가 검토
- **기준 민감도**: 1.5 기준을 1.0~2.0으로 바꿨을 때 유형 분포가 얼마나 바뀌는지 분석
- **모델**: Laya 같은 최신 인코더 파인튜닝 비교, 규제 항목별 단독 효과 측정
- **해설**: GPU 서버가 생기면 로컬 qwen2.5:7b로 교체해 외부 전송 없애기, LLM 호출 추적(tracing)
- **운영**: 시연·발표 전에 요청 제한 한도를 환경변수로 올리거나 끄기, IP 대신 세션 단위 제한 검토, 오류 문구에 "요청이 많아요(제한)"처럼 원인이 보이게 구분

### 운영 오류에서 배운 것
- 오류 문구 하나("잠시 후 다시 시도해 주세요")로 원인을 좁힐 수 있었다. 서버 코드에서 같은 문구를 쓰는 곳이 요청 제한 하나뿐이었다.
- 남용 방지 장치는 **사용 환경**(같은 와이파이 여러 명)을 함께 생각해야 한다. 혼자 테스트할 때는 절대 드러나지 않는다.
