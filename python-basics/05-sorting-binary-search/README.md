## 오늘 배운 것

### 1. 왜 알고리즘인가: 같은 답, 다른 비용
- 둘 다 정답을 내는 코드여도 **입력이 커질 때 얼마나 느려지는가**가 다름
- 어제 두 수의 합: 이중 루프는 20만 개를 못 풀고, 딕셔너리는 순식간에 풂

| | 짝 찾는 방법 | 20만 개일 때 |
|---|---|---|
| 이중 루프 | 안쪽 `for`로 **전부 훑기** | 약 200억 번 (20만 × 20만 ÷ 2) |
| 딕셔너리 | `target - n in seen`으로 **한 번 묻기** | 약 20만 번 |

```python
# 리스트: in이 앞에서부터 하나씩 비교 → 느림
11 in [2, 7, 11, 15]                 # 2? 7? 11? … 최악이면 전부

# 딕셔너리: in이 키 위치로 바로 감(해시) → 빠름
11 in {2: 0, 7: 1, 11: 2, 15: 3}     # 몇 개가 있든 거의 한 번
```
- 속도 차이는 **딕셔너리**에서 나옴. `seen = []`(리스트)로 바꾸면 다시 느려짐

### 2. 순차 정렬: 앞자리부터 하나씩 확정
```python
def sequential_sort(items):
    arr = items.copy()                            # 원본은 그대로, 복사본을 정렬
    n = len(arr)
    for i in range(n - 1):                        # i번째 자리에 들어갈 값을 정한다
        for j in range(i + 1, n):                 # i 뒤의 모든 값과 하나씩 비교
            if arr[i] > arr[j]:
                arr[i], arr[j] = arr[j], arr[i]   # 더 작은 값을 i번째로
    return arr
```
- **고정된 i번째**를 그 뒤 **모든** 값과 비교 → 한 바퀴마다 가장 작은 값이 앞에 확정
- 비용: n(n−1)/2번 비교 → **n이 2배면 4배** 느려짐

**왜 `copy()`를 하나?**
- 파이썬은 리스트를 함수에 넘길 때 **복사본이 아니라 같은 리스트 자체**를 넘김
- 함수 안에서 자리를 바꾸면 밖의 원본도 같이 바뀜
```python
arr = items          # ❌ 복사 아님: 같은 리스트에 이름표만 하나 더
arr = items.copy()   # ✅ 새 리스트 → arr를 바꿔도 items는 그대로
```

### 3. 버블 정렬: 이웃끼리 바꾸면 큰 것이 뒤로
```
[5, 2, 9, 1]
 5>2 바꿈   → [2, 5, 9, 1]
 5<9 그대로 → [2, 5, 9, 1]
 9>1 바꿈   → [2, 5, 1, 9]   ← 한 패스 끝: 가장 큰 9가 맨 뒤
```
- 두 칸 바꾸기는 한 줄: `a[j], a[j + 1] = a[j + 1], a[j]`
- 한 패스마다 뒤에서부터 하나씩 확정 → n−1번 패스하면 정렬 완료
- 비용: 약 n²/2번 비교. 2000개는 0.1초 안이지만 100만 개는 몇 시간

**순차 정렬 vs 버블 정렬: 비용은 같고 비교 방식이 다름**

| | 순차 정렬 | 버블 정렬 |
|---|---|---|
| 비교 대상 | 고정된 i번째 vs 그 뒤 **모든** 값 | 항상 **바로 옆** 두 개 (j, j+1) |
| 한 바퀴 끝나면 | 가장 **작은** 값이 **맨 앞** | 가장 **큰** 값이 **맨 뒤** |

- 버블 정렬은 한 바퀴 동안 한 번도 안 바꿨으면 이미 정렬된 것 → 일찍 멈출 수 있음

### 4. 이진 탐색: 정렬되어 있으면 반씩 버린다
- **업다운 게임**과 같음: 가운데를 찍고 "업/다운"으로 반을 버림 → 1~100은 7번이면 끝

```
[1, 3, 5, 7, 9, 11, 13]에서 11 찾기
 lo=0, hi=6 → mid=3, 값 7  < 11 → 왼쪽 버림, lo=4
 lo=4, hi=6 → mid=5, 값 11 == 11 → 찾음, 5
```
- `lo`, `hi` = **아직 답이 있을 수 있는 범위**의 양 끝, `mid = (lo + hi) // 2`
- 가운데 값이 **작으면** `lo = mid + 1`, **크면** `hi = mid - 1`
- `lo > hi`가 되면 범위가 비었으니 **없음(-1)**
- **전제는 정렬**: "7이 11보다 작으니 7의 왼쪽은 전부 11보다 작다"는 정렬돼 있을 때만 성립

| 데이터 개수 n | 순차 탐색(최악) | 이진 탐색(최악) |
|---|---|---|
| 100 | 100번 | 7번 |
| 100만 | 100만 번 | 20번 (2²⁰ ≈ 100만) |
| 10억 | 10억 번 | 30번 |

- 개수가 2배가 돼도 이진 탐색은 **딱 1번**만 늘어남
- 정렬 비용을 한 번 내면 그 뒤 탐색은 계속 싸게 할 수 있음

### 5. 실무: 정렬과 이진 탐색은 이미 있다
| 오늘 직접 만드는 것 | 파이썬에 이미 있는 것 |
|---|---|
| 정렬 (`bubble_sort`) | `sorted()` (C로 만든 빠른 정렬, 4000개 1ms 미만) |
| 이진 탐색 (`binary_search`) | `bisect` 모듈 (bi 둘로 + sect 나누다) |

```python
import bisect
sorted([5, 2, 9, 1])          # [1, 2, 5, 9]  정렬된 새 리스트

s = [1, 3, 5, 7, 9]           # 위치 0 1 2 3 4 (반드시 정렬된 리스트)
bisect.bisect_left(s, 5)      # 2: 5를 끼워 넣는다면 기존 5의 앞
bisect.bisect_right(s, 5)     # 3: 같은 값이 있으면 그 뒤
bisect.bisect_left(s, 6)      # 3: 없는 값도 들어갈 자리를 알려 줌
```
- `bisect`는 "어디 있나"가 아니라 **"끼워 넣는다면 몇 번 자리인가"**를 알려 줌
- `left` = 그 값이 시작하는 자리, `right` = 그 값이 끝난 다음 자리
- **`right - left` = 그 값의 개수** → 실무 1(`count_between`)의 원리
```python
scores = [55, 62, 70, 70, 78]
bisect.bisect_right(scores, 70) - bisect.bisect_left(scores, 70)   # 4 - 2 = 2 → 70이 2개
```
- 그래도 직접 만드는 이유: 안에서 무슨 일이 일어나는지 알아야 "왜 느린지", "왜 정렬이 먼저 필요한지" 판단 가능
