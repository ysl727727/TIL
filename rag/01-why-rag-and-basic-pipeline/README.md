# 1장. RAG가 필요한 이유와 기본 파이프라인

> 2026-10-19 학습 기록. RAG 1일차 오전 수업입니다. 가상 사내 규정 12개로 "현행 규정 고르기 → 역색인 만들기 → 검색 결과를 Context로 묶기 → 전체 입력과 검색 입력 중 고르기"까지 RAG 파이프라인을 작게 한 바퀴 돌렸습니다. 네 강의 실습 문제(q\_easy·q\_hard)를 모두 직접 풀었습니다.

## 학습 목표

- RAG가 `질문 → 검색 → Context 구성 → 답변 생성` 순서로 문서를 답변 근거로 쓴다는 점을 설명한다.
- **검색 실패**(표현이 달라 못 찾음)와 **검색은 됐지만 문서에 답이 없음**을 구분한다.
- Indexing(미리 준비)과 Query(질문 때 조회)의 역할과 실행 시점을 구분하고, 문서가 바뀌면 인덱스도 다시 만들어야 하는 이유를 설명한다.
- 검색 후보(`rows`)와 모델에 실제로 들어간 입력(`context`, `sources`)을 따로 확인한다.
- 문서 예산을 계산하고, RAG·Long Context·CAG의 역할을 구분해 먼저 비교할 방식을 고른다.

## 실습 파일

| 강 | 주제 | 실습 상태 |
| --- | --- | --- |
| 1-1 | RAG가 필요한 이유와 적용 조건 — 현행 필터, 검색 성공 vs 답변 가능 | ✅ 완료 |
| 1-2 | Indexing과 Query 파이프라인 — 역색인, OR·AND 검색, 인덱스 갱신 | ✅ 완료 |
| 1-3 | 2-Step RAG 기준선 — BM25 검색, 문자 예산 Context, 출처 라벨 | ✅ 완료 |

실습은 수업에서 받은 `rag_day1` 키트(1·2장 8개 강의 폴더 + 공통 uv 환경)로 진행했습니다. 강마다 `main.py`를 실행한 뒤 `q_easy.py`(빈칸)와 `q_hard.py`(직접 구현)를 풀어 정답 확인까지 마쳤습니다. 키트 코드는 올리지 않고 실행 결과와 이해한 내용만 기록합니다.

## 전체 흐름

### 한 문장

**모델이 모르는 우리 회사 규정은, 질문할 때마다 찾아서(검색) 같이 보여 줘야(Context) 근거 있는 답을 받을 수 있습니다.**

### 왜 필요한가

```text
질문: "출장 숙박비는 얼마까지 정산되나요?"
모델만 쓰면   → 일반적인 출장 제도는 알아도 "우리 회사의 현재 한도"는 모름
RAG를 쓰면   → 현행 규정(travel: 1박 12만원, 영수증 필요, 초과 시 사전 서면 승인)을 찾아 같이 입력
```

**비유:** 시험을 오픈북으로 보는 것과 같습니다. 학생(모델)의 머리(가중치)는 그대로인데, 시험 볼 때마다 필요한 페이지를 펴서(검색) 옆에 두고(Context) 답을 씁니다. 다만 **엉뚱한 페이지나 옛날 판(구버전) 교재를 펴면** 틀린 답이 나옵니다.

### 그림으로 보기

```text
[준비: Indexing]  documents.json (12개: 현행 10 + retired 2)
                    │ status == "current" 필터
                    ▼
                  현행 10개 → 청크 28개 → 검색용 인덱스(역색인 / BM25)

[질문: Query]     질문 ─→ 검색 후보 rows (k=3, 점수순)
                              │ build_context(max_chars=260)  ← 예산 넘는 후보는 통째로 제외
                              ▼
                         context(S1, S2 …) + sources ─→ 생성 모델 ─→ 답변 + citations
```

### 강의 흐름

1. **1-1 근거가 필요하다** — 현행 규정만 고르고, 검색 결과에 실제로 답이 있는지 본문을 읽어 확인. 질문·근거·지시문을 하나의 prompt 문자열로 조립.
2. **1-2 미리 준비한다** — 단어 → 문서 ID 집합(역색인)을 만들어 두고, 질문이 오면 조회해서 `by_id`로 본문을 다시 꺼냄. 문서가 바뀌면 인덱스도 다시 만듦.
3. **1-3 모델 입력으로 만든다** — 기준선 설정(80자/20자 청킹, BM25 k=3, 예산 260)을 고정하고, 검색 후보 → Context → 출처를 각각 출력해 비교. 선택 실습으로 Ollama 답변까지 연결.
4. **1-4 방식을 고른다** — 전체 입력 vs 검색 후 입력, 문서 예산 계산, RAG·Long Context·CAG 역할 구분, 상황별 비교 후보 선택.

## 핵심 이론

### 1. RAG는 답변 전에 근거를 찾는다 (1-1강)

- **RAG**(Retrieval-Augmented Generation) = 질문과 관련된 자료를 검색해 모델 입력에 보태고 답변을 생성하는 방식. 문서를 넣어도 **모델 가중치는 바뀌지 않습니다.**
- 질문마다 필요한 자료와 방식이 다릅니다.

| 요청 | 필요한 자료 | 시작할 방식 |
| --- | --- | --- |
| 회사 출장 숙박 한도는? | 현행 출장 규정 | 규정 검색 후 답변 생성 |
| 지금 내 교육비 잔액은? | 개인별 승인·사용 내역 | 인증된 업무 API 조회 |
| 첨부한 한 페이지 요약 | 이미 전달된 문서 | 문서를 직접 입력 |

- **같은 주제라도 현재 버전을 골라야 합니다.** `travel`(current, 1박 12만원) vs `travel-old`(retired, 1박 8만원) → `d["metadata"]["status"] == "current"`인 문서만 검색 후보로 둠.
- **검색 성공 ≠ 답변 가능**

| 검색어 | 결과 | 해석 |
| --- | --- | --- |
| `숙박 비용` | `['travel']` | 같은 표현과 정산 규정이 있음 → 답변 가능 |
| `호텔비` | `[]` | 답은 있는데 **글자가 달라** 검색 실패 → 이후 임베딩 검색으로 다룸 |
| `개인 취미` | `['education']` | 검색은 됐지만 문서에 "지원 여부는 규정되어 있지 않다"고 적힘 → "확인 불가"로 안내 |

- prompt = 지시문("문서를 근거로 답하고, 근거가 없으면 확인 불가") + `[문서 ID] 본문` + 질문. 금액뿐 아니라 **단위와 조건**(영수증 첨부, 초과 시 예약 전 서면 승인)까지 원문대로 전달해야 합니다.
- 실습 `find_policy(term, current_only=True)`: 공백 검색어는 `ValueError`(빈 문자열은 모든 본문에 포함되므로 그냥 두면 전체가 검색됨) → `current_only`에 따라 `current` 또는 `documents`를 검색 범위로 → 본문 포함 여부로 필터.

### 2. Indexing과 Query, 역색인 (1-2강)

| 구분 | 입력 | 출력 | 실행 시점 |
| --- | --- | --- | --- |
| Indexing | 원문 문서 | 단어별 문서 ID 사전 | 문서를 준비하거나 갱신할 때 |
| Query | 검색어 + 준비된 사전 | 관련 문서 ID와 본문 | 질문을 받을 때 |

- 단어 추출: `re.findall(r"[가-힣a-zA-Z0-9]+", text)` → `영수증을`, `한도는`처럼 **조사가 붙은 채** 저장됨(형태소 분석 아님).
- 역색인: `defaultdict(set)`에 `postings[word].add(doc_id)` → 한 문서에 단어가 여러 번 나와도 ID는 한 번만.
- 역색인은 **ID만** 돌려주므로 `by_id = {d["document_id"]: d for d in current}`로 본문·제목을 다시 꺼내야 모델에 넘길 수 있음.
- **OR = 합집합**(`ids.update(...)`), **AND = 교집합**(`intersection_update`).

| 검색어 | OR | AND |
| --- | --- | --- |
| `숙박 교육비는` | education, travel | `[]` |
| `숙박 영수증을` | education, travel | travel |
| `숙박 영수증` | — | `[]` (travel에는 `영수증을`만 있음) |

- AND에서 첫 집합은 `set(index.get(...))`로 **복사**해서 시작. `intersection_update`는 집합을 직접 고치므로, 복사하지 않으면 저장된 색인이 망가집니다.
- 문서를 추가·수정·삭제해도 **이미 만든 인덱스는 자동으로 바뀌지 않습니다.** remote 추가 전 인덱스(`before`)는 새 인덱스를 만든 뒤에도 여전히 `[]`. 인덱스를 다시 만들고 Query가 새 인덱스를 읽게 연결해야 합니다.

### 3. 2-Step RAG 기준선 — 검색 후보와 실제 입력은 다르다 (1-3강)

- **2-Step RAG** = 검색 → 생성. **기준선** = 개선 전후를 비교할 출발점이라 설정을 고정해 기록합니다.

| 고정할 항목 | 이번 기준선 |
| --- | --- |
| 원문 | 규정 12개, 검색 대상은 현행 문서 |
| 청킹 | 최대 80자, 겹침 20자 (이동 간격 60) |
| 검색 | BM25, 최대 3개 후보 |
| Context | 문자 예산 260, 출처 라벨 포함 |

- 12개 문서 → 청크 28개. travel(148자) → `[0:80]`, `[60:140]`, `[120:148]`.
- `출장 숙박 비용 한도는?` 검색 결과: 1위 travel(10.456), 2·3위 meal 두 조각. 점수는 정답 확률이 아니고, 1위 청크도 `…담당 임원의 서면`에서 끊겨 있음.
- `build_context(rows, max_chars=260)`: 후보마다 `본문 + 라벨·제목(14) + 줄바꿈 여유(2)`로 예산을 계산.

| 후보 | 이번 사용량 | 누적 | 결과 |
| --- | --- | --- | --- |
| travel 첫 청크 | 80 + 14 + 2 = 96 | 96 | 포함 (S1) |
| meal 두 번째 청크 | 55 + 14 + 2 = 71 | 167 | 포함 (S2) |
| meal 첫 청크 | 80 + 14 + 2 = 96 | 263 | **제외** — 남은 만큼 자르지 않고 통째로 건너뜀 |

- `S1`, `S2`는 **이번 응답에서만 쓰는 라벨**이지 고정 문서 ID가 아닙니다. `sources`는 Context에 **실제로 들어간 것만** 라벨과 원문 ID를 연결합니다.
- 선택 실습(Ollama `gemma3:4b-it-q4_K_M`, 교안 예시 출력): `answered` / "1박당 12만원입니다. S1" / `['S1']` → 금액은 맞지만 영수증 조건이 빠짐. `insufficient`(근거 부족)면 citations는 빈 목록이어야 하고, 출처가 비어 있으면 모델을 부르지 않고 바로 보류.
- 실습 `prepare_input(question, chunks, k=2)`: 검색 → Context → `{"question", "context", "sources"}` 반환. `재택근무는 주 몇 회인가요?`는 후보가 remote 하나뿐이라 S1 하나만 연결됨.

### 4. 문서 예산과 RAG · Long Context · CAG (1-4강)

- 전체 입력(현행 10개, 1,434자) vs 검색 후 입력(travel 1개, 157자). 이 숫자는 **문자 수**라 토큰 수·요금·속도가 아닙니다.

| 비교 | 문서 전체 입력 | 검색 후 입력 |
| --- | --- | --- |
| 장점 | 검색 단계에서 놓치지 않음 | 관련 자료로 입력을 줄임 |
| 확인할 점 | 많은 자료에서 필요한 조건을 찾는지 | 필요한 문서를 빠뜨리지 않는지 |

- **문서 예산 = 전체 한도 − 지시문 − 질문·대화 이력 − 출력 예약 − 여유분**
  - `8192 − 500 − 500 − 1000 − 192 = 6000`, 출력 예약 3000이면 4000, 이력 1500이면 5000. `max(0, …)`로 음수는 0.
- 세 용어는 **같은 축의 선택지가 아닙니다.**

| 용어 | 역할 | 예 |
| --- | --- | --- |
| RAG | 필요한 외부 자료를 검색해 생성에 사용 | 숙박 규정을 찾아 넣음 |
| Long Context | 긴 입력을 처리하는 모델 능력 | 규정 전체나 더 많은 검색 결과를 입력 — RAG와 **같이 쓸 수 있음** |
| CAG | 미리 넣은 자료의 **계산 상태**(KV cache, prefix cache) 재사용 | 같은 규정으로 반복 질문할 때 공통 앞부분 계산을 재사용 |

- KV cache 재사용 ≠ 완성 답변 캐시. 입력 계산만 재사용하고 **답변은 매번 새로 생성**합니다.
- 캐시 키: `sha256(json.dumps([model, scope, text]))` → 같은 조건이면 같은 키, 모델이나 범위가 바뀌면 다른 키. **키가 같다고 캐시 적중·속도 향상이 검증된 것은 아님.**
- 실습 `choose_input(document_tokens, available, repeated, cache_supported)`

| 조건 (위에서부터 확인) | 반환 |
| --- | --- |
| 문서 토큰 > 예산 | `"RAG 또는 문서 범위 축소"` |
| 예산 안 + 반복 요청 + 캐시 지원 | `"전체 입력 + prefix cache 비교"` |
| 그 외 | `"전체 입력부터 비교"` |

## 질문과 새로 알게 된 점

### 오늘 배운 점

> **검색 후보와 실제 입력은 다릅니다.** `retrieve`가 돌려준 `rows`(후보)와 `build_context`가 만든 `context`/`sources`(모델에 실제로 들어간 것)를 따로 봐야 합니다. 출처는 Context에 **실제로 들어간 것만** 연결해야 합니다.

### 파이썬 문법에서 헷갈렸던 것

| 질문 | 핵심 |
| --- | --- |
| `d["content"]` vs `["content"]` | `d`가 있어야 "그 문서의 본문". 없으면 `"content"` 글자 하나가 든 새 리스트 |
| `A if 조건 else B` | 조건이 True면 A, False면 B. `current_only`는 True/False 값 하나 |
| `set()` 복사 | `intersection_update`는 집합을 직접 고쳐요. 복사하지 않으면 원본 색인이 망가짐 |

### 실습 문제에서 한 실수

| 강의 | 실수 | 수정 |
| --- | --- | --- |
| 1-3 | `row =`로 받고 `rows`를 사용해서 `main.py`에 있던 다른 검색 결과가 쓰임 | 이름을 `rows`로 통일, `k=k`로 인자 전달 |
| 1-4 | 반환 문자열을 `"전체입력 또는…"`으로 씀 | `"전체 입력 + prefix cache 비교"` — `assert`는 글자 하나까지 비교 |

### 개념 정리

| 질문 | 답 요약 |
| --- | --- |
| 예산 초과를 먼저 확인하는 이유 (1-4) | 들어가지 않는 입력은 캐시할 수도 없어요. 가능한지 먼저, 최적화는 나중 |
| 세 반환값의 의미 (1-4) | 초과 → RAG 또는 범위 축소 / 들어가고 반복+캐시 → 전체 입력+캐시 / 그 외 → 전체 입력부터. 모두 실험할 "후보"이지 결론이 아님 |
| KV cache 재사용 시 이전 답변이 그대로 나온다? | 아니에요. KV cache는 입력 계산 상태를 재사용하고 답변은 매번 새로 생성. 답변을 그대로 돌려주는 건 응답(완성 답변) 캐시 |
| 검색 후보 vs 실제 입력 | `retrieve`의 `rows`와 `build_context`의 `context`/`sources`. 출처는 Context에 실제로 들어간 것만 연결 |

## 확인 문제

강의 내용을 바탕으로 직접 만든 복습 문제입니다. 객관식 4문제, 서술형 2문제이고 각 문제 바로 아래에 정답이 있습니다.

### 1-Q1. 검색은 됐는데 답할 수 없는 이유 (1-1)

`개인 취미`로 검색하면 education 문서가 나오는데도 "개인 취미 강좌도 지원되나요?"에 답할 수 없는 이유는?

① 검색어 표현이 달라 문서를 찾지 못해서  
② 폐기된(retired) 문서가 Context에 섞여서  
③ 문서는 찾았지만, 그 문서에 지원 여부가 정해져 있지 않아서  
④ 모델 가중치에 그 정보가 학습되어 있지 않아서

<details>
<summary>정답 보기</summary>

**③** — 검색은 성공했지만 education 본문에 "개인 취미 강좌의 지원 여부는 이 문서에 규정되어 있지 않습니다"라고 적혀 있어요. "확인 불가"로 안내해야 합니다. ①은 `호텔비`처럼 표현 차이로 검색에 실패한 경우예요.

</details>

### 1-Q2. OR 검색 결과 (1-2)

역색인으로 `숙박 영수증을`을 OR 검색했더니 travel뿐 아니라 education도 나왔다. 이유는?

① education에도 `영수증을`이 있어서, 단어별 문서 집합을 합치는(합집합) 과정에서 포함됐다  
② 두 단어가 모두 있는 문서만 남기는 AND 검색이라서  
③ 문서를 바꾼 뒤 인덱스를 다시 만들지 않아서  
④ BM25 점수가 높은 문서부터 보여 줘서

<details>
<summary>정답 보기</summary>

**①** — `숙박` → {travel}, `영수증을` → {travel, education}을 합집합으로 모으면 둘 다 나와요. AND(교집합)로 바꾸면 travel만 남습니다.

</details>

### 1-Q3. 후보 3개, Context 2개 (1-3)

기준선(k=3, 문자 예산 260)에서 검색 후보는 3개인데 Context에는 2개만 들어갔다. 이유는?

① 검색 함수가 실제로는 k=2로 동작해서  
② 세 번째 후보의 BM25 점수가 0이라서  
③ 세 번째 후보가 retired 문서라 필터돼서  
④ 세 번째를 넣으면 누적 263으로 예산 260을 넘어서, 그 후보를 통째로 건너뛰어서

<details>
<summary>정답 보기</summary>

**④** — 96 + 71 = 167까지 들어가고, 세 번째(96)를 더하면 263이에요. `build_context`는 남은 공간만큼 자르지 않고 후보 전체를 건너뜁니다.

</details>

### 1-Q4. RAG · Long Context · CAG (1-4)

설명으로 옳은 것은?

① Long Context 모델을 쓰면 검색(RAG)은 항상 필요 없다  
② RAG와 Long Context는 함께 쓸 수 있고, CAG는 공통 자료의 계산 상태를 재사용한다  
③ KV cache를 재사용하면 이전 답변 문장이 그대로 반환된다  
④ 캐시 키(해시)가 같으면 캐시 성능 검증까지 끝난 것이다

<details>
<summary>정답 보기</summary>

**②** — ①: 검색한 근거를 긴 입력 모델에 넣을 수 있어요. ③: 완성 답변 캐시와 혼동한 설명이에요. ④: 실제 적중 여부와 처리 시간을 따로 측정해야 합니다.

</details>

### 1-Q5. 서술형 — 두 가지 실패 (1-1)

`호텔비` 검색이 빈 결과인 것과 `개인 취미` 질문에 답할 수 없는 것은 원인이 어떻게 다른가요? 각각 어떻게 대응하면 좋을까요?

<details>
<summary>예시 답안</summary>

- 호텔비: 답은 travel에 있지만 "숙박 비용"과 **글자가 달라 검색 단계에서 실패**. → 뜻으로 찾는 임베딩(Dense) 검색이나 동의어 처리로 개선.
- 개인 취미: 검색은 성공했지만 **문서에 답이 없음**. → 검색을 고칠 문제가 아님. 단정하지 말고 "제공된 문서에서 확인할 수 없음"으로 답하게 함.

</details>

### 1-Q6. 서술형 — 출력 예약과 입력 한도 오류 (1-4)

출력 예약을 1,000토큰에서 3,000토큰으로 늘렸더니 입력 한도 오류가 났다. 문서 예산 공식으로 원인을 설명하세요. (전체 8,192 / 지시문 500 / 질문·이력 500 / 여유 192)

<details>
<summary>예시 답안</summary>

문서 예산 = 8192 − 500 − 500 − 출력 예약 − 192. 출력 예약 1,000이면 6,000, 3,000이면 4,000토큰이에요. 출력 예약을 늘린 만큼 문서 공간이 줄었는데 문서를 예전처럼 넣어서 한도를 넘었습니다. 검색 후보 수나 Context 예산을 줄이거나 출력 예약을 다시 조정해야 하고, 문자 수가 아니라 Tokenizer로 센 토큰 수로 확인해야 해요.

</details>
